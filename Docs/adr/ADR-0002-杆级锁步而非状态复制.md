## 1. 决策一：网络只同步"这一杆的参数"，不同步球状态

### 背景

本工程的物理是**自研二维定长步进内核**（`PoolSimulator`，`FixedDeltaTime = 1/120`），
**禁用 Unity PhysX**（铁律：离散检测在开球堆球时穿透，且无确定性）。
一场双人局的可同步对象只有两类：

- **A. 状态**：16 颗球 × `(position, velocity)` × 每秒 120 次 ≈ 7680 个 float/秒；
- **B. 输入**：一杆 = 瞄准角 + 力度（量化后 6 字节），一局约 100 杆。

### 决策

**选 B。** 两端各跑同一套物理；网络上只走"杆命令"，球的位置/速度**只出现在校验与重同步里**，不出现在常规帧里。

### 理由

1. **载荷差两个数量级**：A 约 30 KB/s，B 约 30 B/杆。局域网也不是免费的，但这不是主因。
2. **权威问题被简化**：若同步状态，就必须回答"谁的状态算数、另一端的球为什么会瞬移"。
   同步输入时这个问题**不存在** —— 球的位置是双方各自从输入**推出来**的，不是"收到的"。
3. **本工程已经具备做这件事的前提**，且是**实测**的，不是希望：
   - 内核**零三角函数**（`grep` 实测 0 命中），只有 `Min/Max/Abs/Clamp` + `PoolMath.Sqrt`，
     即 `+ − × ÷ sqrt` —— IEEE-754 保证这五个**正确舍入**，跨 ISA 位相同；
   - 唯一未收口的超越函数是 `CueVelocityFor` 的 `Mathf.Cos/Sin`（每杆一次），
     已由"白球初速 `v0` 由房主算好下发"在协议层消除；
   - 规则层 `EightBallRules.Judge` 是**纯函数**，不读时间/随机。
4. **反例是具体的**：改用状态复制（Netcode for GameObjects 那一类）意味着把整局状态搬进
   `NetworkBehaviour`、引入引擎自带 tick 与自研累加器并存的第二套时钟，
   并重写 35-C 花一整轮才稳定的结算管线。代价远高于收益，且**没有**解决任何一个本工程的实际问题。

### 后果

**接受的代价**：

- 两端必须**加载完全相同的物理输入**（桌几何、物理参数、规则版本）⇒ 必须有握手期的
  `contentHash` 比对，不一致就**拒绝开局**（不许"先打着看"）。
- 跨平台浮点漂移**不可能被消除，只能被检出** ⇒ 必须有每杆校验和（见决策二）。
- 摆球必须由**种子**决定而不是"发 15 个坐标"⇒ 种子→摆法的映射必须**有契约**。
  ⚠ 现状不满足：`PhysicsTestDrive.cs:2151` 用了 `System.Random`，而工程自己在
  `EightBallAi.cs:130/:636` 明令禁止它。这一条已作为 P0 单独处理（正文 §5.6）。

**放弃的东西**（明确不做）：观战（旁观者不跑物理就只能收状态流 = 另一套协议）、
回放分享（日志天然可回放，但导出格式不做）、跨平台定点数改造（先检测，不先上定点）。

## 2. 决策二：每杆一个校验和，不一致时以**房主**为准

### 背景

锁步把"结果"变成了"两端各自推导的结果"。两端**迟早**会分叉（浮点、FMA 收缩、
桌数据没同步、某个分支只在一端触发）。分叉若不被发现，后果是**两个人都认为自己赢了**。

### 决策

1. **每杆结束后**，双方各自算一个**量化后**的状态摘要（位置 1 mm、速度 1 mm/s，
   离散状态 `frozen` / `capturedPocket` 原样），并交换。
2. **同时**比对离散规则事实（首碰球号、进袋顺序、碰库集合）—— 这些**即使球位置差 < 1 mm 也可能翻转**，
   必须单独比。
3. 不一致时：**房主的状态是唯一权威**，客户端整体覆盖后回读摘要确认；
   连续 2 次仍不一致 ⇒ 干净中止（`Bye{reason=desync}`），**不判任何人胜**。

### 理由

1. **"以谁为准"必须有单一答案。** 若允许"谁先发现谁算"，两端可以互相覆盖到永久循环。
   房主权威是**唯一**不需要额外机制的选择（房主已经在决定摆球种子与回合归属）。
2. **量化是必须的，不是优化。** `float32` 在 1.27 m 处的 ulp ≈ 0.12 µm；
   一杆几千步的随机游走累积量级 ≈ 10 µm。1 mm 步长相对它留约 100× 余量 ⇒
   **良性噪声不会误报**，而 1 mm = 1/28.6 个球直径 ⇒ **任何真实分歧当杆必被检出**。
   不做量化就必须比 float 位相等，那是"必然误报"。
3. **为什么发"每球量化向量"而不只发哈希**：只发哈希只能知道"某处不一样"；
   发向量能直接得到"3 号球偏了 4.7 mm"，且让阈值可以按**实测**校准而不是靠猜。成本 128 B/杆。
4. **为什么先检测、不先上定点数**：内核除 `Sqrt` 外只有加减乘除，已经是"定点友好"形态，
   真需要时改造路径清楚。但现在上定点要改 `RestSpeedThreshold` / `StoppedSpeedEpsilon` /
   `ContactArcErrorBound` 等一整套阈值的量纲 ⇒ 35-C 调好的手感要重新标定。**这是真实成本，不能白付。**

### 后果

**接受的代价**：

- `PoolSimulator` 必须新增 `CaptureSnapshot` / `RestoreSnapshot`（当前**没有**，且状态不止
  `position/velocity` —— 还有 `_frozen` / `_capturedPocket` / `_vAvg` / `ConsecutiveRestFrameCount`；
  `LoadBalls` 会清掉前两者，**不能**用来恢复）。
- 摘要算法（FNV-1a 32）**只允许有工程内一处实现**，并用金向量钉住。理由是本轮实测：
  两份自己写的 FNV 对同一组输入给出了**不同**的摘要（`uint32` 乘法溢出边界处理不同）
  ⇒ **"各写一遍"本身就会引入漂移**。
- 每杆多一轮往返（LAN 上 5 ms 级），换来的是"分叉当场可诊断"。

**放弃的东西**：不做"零分歧"的强承诺。本方案承诺的是**分歧一定被检出且不静默**，
不是"分歧不会发生"。这个区别写进 ADR，避免以后有人拿"应该零分歧"来要求重写内核。

## 3. 被本 ADR 否掉的备选方案

| 备选 | 否决理由 |
| --- | --- |
| Netcode for GameObjects（状态复制 + `NetworkTransform`） | 见决策一理由 4：载荷差两个数量级、引入第二套时钟、要重写结算管线。且**项目根本没装**（`Packages/manifest.json` 只有待删的 `com.unity.multiplayer.center`） |
| 客户端上报结果、房主记账（"可信客户端"） | 客户端上报"我赢了"是**零成本作弊**。锁步的全部价值就是"结果由输入推出，不由声称推出" |
| 房主跑物理、客户端只收球位置 | 这是"状态复制"的另一种写法，且丢掉了"两端都能本地预测"的能力 ⇒ 客户端每次击球都有 RTT 延迟 |
| 直接上定点数内核 | 见决策二理由 4：需求尚未被证明存在，改造面是全内核 + 全部阈值重新标定 |
| UDP + 应用层重传 | 回合制、每秒 1–2 条消息、丢一条 = 对局卡死 ⇒ 等于重新实现一遍 TCP，且实现得比 TCP 差 |

## 4. 与既有 ADR 的关系

- `ADR-0001`（坐标系与手性）不受影响：本 ADR 不引入任何新的坐标转换。
- 本 ADR **依赖** ADR-0001 的一个结论：物理在**规范二维米制平面**运算、渲染层才映射到 Unity 世界。
  锁步只在**物理平面**上校验，因此不受渲染层缩放（`PlayfieldVisualScale = 1.2`）影响。
