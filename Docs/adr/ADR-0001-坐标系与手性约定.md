## 1. 背景与问题

本项目**自研二维定长步进物理模拟器**（不使用 Unity PhysX），碰撞几何完全来自美术交付包的
`table-metadata-reference.json`。整个链路上存在**三个不同的坐标系**，任何一处做错都会让球桌"立起来"、
"整体镜像"或"大 20%"，且**症状安静**（球仍能动，只是手感全错）。交付文档对此明确警告：

> `gameplay-markers-reference.json → coordinates.native_engine_conversion`
> **"Confirm importer handedness, units and axis conversion with TA;
> do not apply both an importer conversion and a second manual conversion."**

即：**同一个轴向/手性转换只允许做一次**；导入器做一次、代码里又做一次，净效果就是错误。

### 三个坐标系（如实标注）

| 系 | 轴约定 | 手性 | 说明 |
| --- | --- | --- | --- |
| 规范二维物理平面 `physics2d` | x = 长轴，y = 短轴，单位米 | — | 直接取自 JSON 的 `collision.segments/pockets`，**不做任何转换** |
| 源运行时三维（three.js/glTF） | +X 长轴、+Y 上、+Z 短轴 | **右手** | JSON 自述 `physics2d.(x,y) == runtime3d.(x,z)` |
| Unity 世界 | +X、+Y 上、+Z | 左手（引擎固定） | 物理平面嵌入 XZ 水平面 |

### 实测暴露出的两个反直觉事实（**这是本 ADR 的核心动机**）

1. **`PoolTable_Normalized.fbx` 声明 `GlobalSettings.UpAxis=Y`，但顶点数据实际是 Blender 原生 Z-up。**
   （独立解析 FBX 二进制核实：顶点包围盒 `Z∈[-0.8635, 0.0610]` 正是"桌面到桌腿底"的竖直范围；
   6 袋 72 个 `runtimeInnerRim` 点到 FBX 顶点的最近距离 = `0.000000 m`，对应映射恰为 `(rx, rz, ry)`。）
2. **Unity 导入该 FBX 时把 X 轴取反**（右手→左手的 handedness 转换），其余轴不变。
   实测 Unity 内网格顶点局部包围盒 `X[-1.412409, 1.412686]`，与源 `(px, py, up)` 相比恰是 `(-px, py, up)`。

**教训（通用）："元数据声称"不能替代"实测"。** 若据 `UpAxis=Y` 就推断 Unity 不做轴转换，实现会整体错位。

## 2. 决策

### 2.1 唯一转换点

**`Assets/_Project/Scripts/Runtime/Core/PoolGeometry.cs` 是全工程唯一的坐标转换入口。**
除此之外，**任何位置**都不得再做轴 / 手性 / 缩放转换。所有跨系读写都必须经过本类的四个 API：

```csharp
PoolGeometry.PhysicsToUnity(Vector2 p, float height)   // 物理二维 → Unity 世界
PoolGeometry.PhysicsToUnity(Vector2 p)                 // 同上，台呢高度 y=0
PoolGeometry.PhysicsBallToUnity(Vector2 p)             // 同上，球心高度 y=BallRadius
PoolGeometry.UnityToPhysics(Vector3 world)             // Unity 世界 → 物理二维（指针拾取）
PoolGeometry.ModelVertexToUnity(Vector3 modelLocal)    // 模型局部顶点 → Unity 世界（仅模型侧一次）
```

### 2.2 唯一转换链（三段式：物理 → 模型局部 → 世界）

```
物理点 (px, py, h)
  │
  ├─ PhysicsToModelLocal = (−px, py, h)        // 模型局部空间（Unity 导入后实测：局部顶点 = (−px, py, up)）
  │                                             //   X 取反来自 Unity 的右手→左手 handedness 转换
  └─ ModelOrientation   = Rx(≈270°)，纯旋转 det=+1
        │
        └─▶ Unity 世界 = (−px, h, −py)
```

**`ModelOrientation` 是模型自带的朝向常量**（来自 FBX 根节点变换，实测 `rootRot=(270.02°,0,0)`）。
它把源 Z-up 几何摆正到 Unity Y-up，因此**属于模型姿态，必须被转换链纳入**，
**而不是**在场景里对球桌实例另加一次手动旋转（见 §7 约束 2）。

### 2.3 唯一物理→世界映射

```
PhysicsToUnity(px, py, h) = ModelOrientation · PhysicsToModelLocal(px, py, h) = (−px, h, −py)
```

**关键点**：该式与"实例化网格的世界坐标"**恰好重合** —— 不是"在某个对称性下近似重合"。
这是 ADR §9 修正后确立的核心不变量，由 `TableIntegrityValidator` 的 `SCN-04`（±0.1 mm）持续断言。

> ⚠ **与 Day 2 版本的差异**：Day 2 曾定为 `(px, h, py)`（"X、Y 均无符号翻转"）。
> 那个式子**只与网格局部顶点比对过**，从未与"实例化后的世界坐标"比对，因而漏掉了 `ModelOrientation`，
> 使两者相差**绕 Y 的 180°**。详见 §9。

### 2.4 单位尺度：canonical 与 displayed 二选一

物理与几何一律使用 **canonical（规范米制）**。"桌面扩大 20%"**只作用于表现层**（`PlayfieldRoot` 的 Transform 缩放 1.2），
指针拾取须**反向映射回物理坐标**。**两者互斥**——把 1.2× 的 displayed 坐标再放进带 1.2 缩放的根节点下，
会让整体变成 1.44×（交付文档 `transforms.anti_double_scaling`）。

## 3. 备选方案与为何不选

| 备选 | 描述 | 为何不选 |
| --- | --- | --- |
| **A. 直接用 `Quaternion.Euler(-90,0,0)` 作为模型修正** | 绕 X 轴 −90°，把"up"从局部 Z 转到世界 Y | **未通过实测**。首版即此方案，导致 AXL-02/04/05 三项失败（640 mm 级误差）。它只对"Unity 不改变 X 符号"的假设成立，而实测 Unity 会取反 X。 |
| **B. 修改 FBX 的 `GlobalSettings.UpAxis` 为 Z（2）** | 让 Unity 的 FBX SDK 自行做 Z-up→Y-up 转换 | 会**改动源资产**，破坏"源 FBX 未被修改"的溯源前提（JSON 记录 `source_unmodified=True`、`source_sha256`），且黑箱依赖导入器内部行为，不可判据。 |
| **C. 在场景里给模型挂一个补偿旋转** | 模型保持原样，用 GameObject 旋转补偿 | 违反"只做一次转换"——会与导入器转换叠加，成为双重转换的温床；且转换点分散、不可判据。 |
| **D. 依赖 JSON 的 `transforms.prototype_playfield_root`（1.2 缩放）** | 照搬原型的根节点变换 | 那是 **displayed（表现层）** 语义，不能进入物理；且与 canonical 混用会触发 anti-double-scaling。 |
| **E（采用）. 实测确定唯一映射，收敛到单一转换点** | 穷举 48 种正交轴候选，取对齐最优者，写死为一处纯旋转 + 一处映射函数 | 见第 5 节的可判据证据。**唯一由实测证据支撑、且满足"只做一次"的方案。** |

## 4. 后果

### 正面

- 物理轮廓与渲染网格严格对齐（82 段端点最大水平偏差 **0.261 mm**）。
- 转换只存在一处，可评审、可回归、可 diff；新增代码无从"顺手再转一次"。
- 为 Day 4+ 的瞄准预测、AI 推演、回放提供了**确定且唯一**的坐标基准。

### 负面 / 需要注意

- 模型轴修正是 (0,1,1)/√2 轴上的 180° 旋转，**不是直觉上的"绕 X 转 −90°"**，容易被后来者"顺手改回去"。
  → 由 `TableConfigTests.ModelAxisCorrection_MapsModelUpToUnityUp_AndPreservesChirality` 与
  `TableIntegrityValidator` 的 AXL-02 持续锁定。
- `ModelVertexToUnity` 只对**模型局部顶点**成立；若将来把多个子网格拆到不同 Transform 下，需重新评估。

### 规范自由度已由转换链消除（原"py 符号不可判别"记录作废）

Day 2 曾记录："`py` 的符号在数据上不可判别（本桌近对称，两符号候选差 1.25e-4 mm）"。
§9 修正后该自由度**不再存在**：`PhysicsToModelLocal` 直接使用**模型自身的局部轴**
（`(−px, py, h)`），因此方向由"模型实际导入姿态"唯一确定，而不是在等价约定中任选一个。

> 保留这条记录的意义：说明"当时为什么看起来有两种读法"，以及**含糊是如何掩盖问题的**。

## 6. 容差策略（明文约定：两类容差不可混用）

本工程存在**两种性质完全不同**的比对，容差必须分别推导，**不得互相套用**：

| 类别 | 定义 | 例子 | 容差 | 理由 |
| --- | --- | --- | --- | --- |
| **(a) 数据集 ↔ 数据集** | **同一批点**的两种表示 | 源 JSON ↔ 生成的 `TableConfig` | **索引对齐 + 逐字段，容差 1e-5 m** | 表示转换应精确到 float 精度；索引对齐下镜像/180° 误差达 0.27~2.6 m，一抓即中 |
| **(b) 数据 ↔ 网格对应** | **两组不同**的点之间求对应 | 82 段端点 ↔ 渲染网格顶点（AXL-04/05） | **轮廓近似残差 ≤ 0.5 mm，且必须输出实测值** | 0.2613 mm 不是误差，而是"82 段直线段逼近曲率袋角"的**轮廓近似残差**；阈值由该测量性质推导（约 1.9× 余量） |

### 铁律

1. **任何"是否镜像 / 是否旋转"的判定，禁止依赖顺序无关比对。**
   独立复核实测：顺序无关口径下，镜像/180° 与真值只差 **0.10~0.47 mm**。镜像/旋转只由下列判据负责：
   `CMP-03`（索引对齐 1e-5）、`CHR-01`/`CHR-02`（自包含手性/绕向）、`AXL-02`（网格外轮廓 x 向 0.277 mm 不对称，容差 1e-4）。
2. **`DAT-09`（库边端点包围盒）抓轴交换/缩放，不抓镜像**——其 x 左右不对称仅 **7.6e-8 m**，低于任何可用容差。已在代码注释中标注，避免误用。
3. **(b) 类检查必须把实测值写进输出**，不能只输出 PASS/FAIL。
   阈值只能拦大错，**记录实测值才能看见渐变漂移**（例如 0.2613 → 0.45 mm 的缓慢退化）。
4. **不得以"删除检查"作为让套件变绿的手段。** 若容差被误用，正确做法是**纠正容差的推导依据并保留检查**；
   一旦"删检查"可用，真正的回归就会以这种方式溜过去。

## 7. 实施约束（给后来者的铁律）

1. **禁止**在 `PoolGeometry.cs` 之外的任何位置做轴 / 手性 / 缩放转换。
2. **禁止**对导入的球桌模型再叠加任何手动旋转。模型自带朝向（`ModelOrientation`）**只活在转换链里**，
   场景/预制件对球桌实例一律保持导入后的姿态，不得再叠加。
3. **禁止**修改 FBX 的 `GlobalSettings` 或顶点数据来"修"轴向（本工程以实测+代码单点处理，不改源资产）。
4. 物理与几何一律用 **canonical 米制**；1.2× 只作用于表现层，且不得与 scaled 坐标混用。
5. 改动 `PoolGeometry` 的任何常量/函数后，必须让 `TableConfigTests`（EditMode）与
   `Billiards/Verify/Validate Table Data & Art (Day 2)` 全绿方可提交。

## 9. 修正记录（Day 3）：模型自带朝向被漏掉，导致不变量"在对称性下近似为真"

### 9.1 发现

Day 3 实例化球桌后实测**世界空间**包围盒：

| | min | max |
| --- | --- | --- |
| 实测 | `(-1.412409, -0.863517, -0.797634)` | `(1.412686, 0.061022, 0.797634)` |
| Day 2 的期望（`OuterBounds*`） | `(-1.412686, -0.863517, -0.797634)` | `(1.412409, 0.061022, 0.797634)` |

**X 端被镜像**，偏差 = 角袋 x 向不对称 = **0.277 mm**；根节点旋转实测 `Rx ≈ 270°`。

### 9.2 根因

Day 2 的 `AXL-02` 只把 `ModelVertexToUnity(mesh.vertices)` 与期望包围盒比对，
**从未与"场景实际变换后的世界坐标"比对** —— 于是漏掉了模型根节点自带的 `ModelOrientation`，
使"物理帧 ↔ 世界"相差绕 Y 的 180°。

**这是一族错误的又一面**：*检查测了一个"方便测的量"，而不是"真正需要成立的那个量"*。
（同族：AXL-04/05 测"最近顶点"而非"最近面点"；生成物守卫测"转写脚本是否变了"而非"记录是否仍与资产相符"。）

### 9.3 修正

把 `ModelOrientation` 显式纳入转换链（§2.2 三段式），使
`PhysicsToUnity(px,py)` 与实例化网格的世界位置**恰好重合**。
**未在场景叠加任何手动旋转**；朝向知识只存在于 `PoolGeometry`。

### 9.4 证伪（检查必须能失败）

以**角袋 x 向不对称 0.277 mm** 为判决量：翻转 `ModelOrientation`（用 `+90°` 代替 `−90°`）后，
`WorldBounds*` 与正确期望的最大偏差跳到 **2.77e-4 m > 1e-4 m 容差** ⇒ `SCN-04` 必然 FAIL。
由 `ModelOrientationTests.Falsification_FlippingOrientationConstant_MakesWorldBoundsCheckFail` 断言并打印实测值。

### 9.5 附：一条被顺带推翻的解释

D2-T03 复核用自写 FBX 二进制解析器证明：188 个端点**全部精确落在网格面上**（最坏 `0.000000 m`）。
此前记录的"0.2613 mm 是**轮廓近似残差**"**已被证伪** —— 它是"端点 → 最近**顶点**"这一度量自身的
**离散采样下限**。故 AXL-04/05 口径改为"端点 → 最近**面点**"，阈值 1e-4 m（见 §5）。
