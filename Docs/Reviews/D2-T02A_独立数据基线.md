## 1. 交叉数据源一致性比对（最重要结论）

### 1.1 判定：两份文件**完全一致（逐位相同，最大绝对差 = 0.0）**

命令：`$PY Docs/Tools/verify_collision_data.py`

- **82 段是否逐段一一对应**：是。逐**索引**对齐后 `a/b` 端点与 `rail` 标签**全部相同**，方向（`a→b` 点序）未被反转（`seg_reversed_detected = 0`）。
- **6 袋几何是否一致**：是。`runtimeCenter`、`captureRadius`、`openingRadius`、`mouth`、`throat` 以及 12 点 `innerRim` 三轴全部 `Δ = 0`。
- 一致精度：**绝对差恰好 `0.0`**（不是 `1e-16`），表明是**逐位拷贝**而非重新计算。

### 1.2 "一致"不是假象 —— 我的确认方式（含最强的反证）

这是本任务最需要谨慎的一句话，逐条列出我为确认它所做的对抗性检查：

1. **覆盖全部而非抽样**：`compare_sources()` 用 `for i in range(len(tseg))` 遍历 **全部 82 段**，6 袋逐字段、`innerRim` 逐**全部 12×3 分量**比对，标量逐项比对。无任何 `[:k]` 抽样。
2. **不是"近似"而是"逐位"**：最大绝对差恰为 `0.0`。若是两段独立计算，浮点末位几乎不可能全部归零。
3. **最强反证——两文件同源，交叉比对只是"漂移检查"，不是"独立佐证"**：
   - `gameplay-markers.sources` 列表中含 `…/public/assets/table-metadata.json`，其 `bytes = 108174`，**恰好等于** `table-metadata-reference.json` 的文件字节数；
   - 其声明的 `sha256 = ba60fc20…364398`，**与我实测 TM 的 sha256 完全一致**；
   - GM 顶层 `validation.source_metadata_rail_equality = true`、`source_metadata_table_equality = true`。
   - **⇒ GM 是由 TM 生成的同源输出。因此"两者一致"只证明 GM 未从 TM 漂移，不能用来佐证几何本身正确。**
4. **无法用"字段更多 = 更可信"来排序**：GM 自称更完整，但就袋几何而言 **GM 是 TM 的严格子集**（见 §1.3）。二者不是两个独立测量，不能互相背书。

### 1.3 一个必须写清的落差：GM 并不比 TM"更权威"

GM 的 6 袋只保留了 `{index, kind, x, y, openingRadius, captureRadius, mouth, throat}`。
以下字段 **TM 有、GM 无**（实测）：

## 3. 轴向与手性分析

### 3.1 坐标系与既有映射（从原始字段推导）

| 系 | 手性 | 上轴 | 备注 |
| --- | --- | --- | --- |
| 源 FBX（Blender 式） | 右手 | **Z** | `source_cloth_z = −0.379`（布面是水平 Z 面） |
| three.js/glTF runtime | **右手** | **Y** | `gameplay-markers.coordinates.world` 明写 "right-handed" |
| Unity | **左手** | Y | 引擎固定 |

- TM `coordinate_mapping = "runtime x=(sourceY−cy)*s, runtime y=(sourceZ−clothZ)*s, runtime z=(sourceX−cx)*s"`，即 `(sx,sy,sz)→(sy,sz,sx)`，是**循环置换（det=+1）**，保持手性 → runtime 确为右手 Y-up。
- GM `blender_from_runtime_xyz = [x, −z, y]`，矩阵 `[[1,0,0],[0,0,−1],[0,1,0]]`，det=+1，是**右手系间旋转**（Blender Z-up ↔ three.js Y-up），**不含手性翻转**。
- **2D 物理平面**：`collision_coordinates` 明确 "2D physics {x,y} uses runtime {x,z}"；GM `physics2d_to_runtime3d`："collider/pocket {x,y} → [x, 0, y]"。即碰撞几何活在**水平面**，竖直分量恒为 0。
- **Unity 侧正确映射**：因 Unity 与 three.js 同为 Y-up，水平面同为 XZ，差异**只在手性**。因此正确映射 = `Unity = (phys.x, 0, ±phys.y)` 中的**某一个**符号约定，且该符号**必须与导入模型网格所用手性翻转一致**、且**全程只应用一次**。
- 交付文档明确警告（GM `coordinates.native_engine_conversion`）：**"Confirm importer handedness … do not apply both an importer conversion and a second manual conversion."**

### 3.3 双重转换专项：哪条判据抓得到，哪条抓不到

双重转换有两种典型形态（症状都很"安静"）：

**形态 A — 双重手性翻转（水平面镜像）**：导入器做了 RH→LH（如 `x→−x`），实现者又手动同向翻一次 → 净效果 = **镜像**。
- **抓不到**：C1（距离不变）、C2（近对称布局）、C5（仍在水平面）、C6（bbox 不变）。
- **抓得到**：**C3（绕向翻号）** 与 **C4（手性符号全翻）**。→ **C4 是唯一"仅看候选数据本身"就能发现镜像的强判据**（前提：保留 mouth 语义序）。
- 若**有基线**：索引对齐逐点比对误差高达 **±2.58 m**，一抓即中（见 §3.5）。

**形态 B — 双重轴向旋转（Z-up↔Y-up 应用两次）**：
- **90°（轴交换）**：**C6 抓得到**（bbox 比 1.9087→0.524）、**C2 抓得到**（corner/side 方位错位）。C1/C3/C4 抓不到（proper 变换保距离、保绕向、保手性）。
- **180° 绕竖直轴**：这是**最危险的一种**——本桌在 180° 旋转下**近乎自对称**（见 §3.4），**C1~C6 全部抓不到**。**只有"索引对齐的逐点比对基线"能靠那 0.277 mm 的不对称勉强区分**（且必须索引对齐或容差足够紧，见 §3.5）。

**一句话结论**：**双重转换最常见的形态（水平面镜像）只能靠 C3/C4 手性判据或逐点基线比对发现；C1/C2/C5/C6 对它整体失效。** 因此 D2-T02B 必须**同时**具备"逐点索引对齐比对"与"手性/绕向校验"两层，缺一不可。

### 3.4 本桌的对称性是"镜像判据失效"的根因（实测）

| 镜像/旋转对称度 | 实测差值 |
| --- | --- |
| 角袋 P0 ↔ P2 的 x（唯一有效不对称） | **2.771e−04 m** |
| 角袋 P0 ↔ P3 的 y | 2.217e−07 m |
| side 袋 P1 ↔ P4 的 x | 2.459e−07 m |
| 全部库边端点的 x 对称 | 7.600e−08 m |
| 全部库边端点的 y 对称 | 0.0 |

**结论**：除角袋中心存在 **0.277 mm** 的 x 向不对称外，整份几何在水平面内**近乎完全镜像对称**。这正是"镜像/180°旋转"类错误难以自检的根因。

### 3.5 容差陷阱（实证，务必写进 D2-T02B 的验收）

若校验器是**顺序无关**（排序 / 最近邻 / 集合）的，各错误变换与真值的最大最近邻距离实测为：

| 变换 | 顺序无关最近邻最大距离 |
| --- | --- |
| identity | 0.0 |
| **mirror_x** | **4.735e−04 m** |
| **mirror_y** | **1.035e−04 m** |
| rot90 | 8.100e−01 m |
| **rot180** | **4.732e−04 m** |

⇒ **顺序无关比对下，镜像与 180° 旋转与真值只差 0.10~0.47 mm。用 1 mm 容差会被完全骗过。**
而**索引对齐**比对下，同样这些错误误差为 0.27~2.6 m，余量巨大。

**因此建议**：D2-T02B 主方法用**索引对齐 + 逐字段比对**，容差 **1e-5 m（10 µm）**；若不得不做顺序无关比对，容差必须 **< 1e-4 m**。
（脚本 `comparison_guidance` 字段已内嵌此结论。）

### 4.1 "只做正向检查（值对不对）"的校验器会漏掉哪些？

把校验器分两类：
- **V-值**：有独立基线，索引对齐逐字段比"值对不对"。
- **V-自洽（"正向"）**：**无基线**，只检查候选自身自洽/合理（段数、rail、连续性、正数、比例如 2:1、对称性等）。

**结论**：如果 V-值做到"逐字段、索引对齐、容差 1e-5"，它**能抓全部** RC-1~RC-7。
真正危险的是——**当实现者只写 V-自洽（或顺序无关的 V-值），会漏掉**：

1. **RC-4 镜像 → 完全漏**。布局近对称 + 不查手性 → 自洽检查全过。**这是最危险的一个**（双重转换最常见形态）。
2. **RC-6 180° 旋转 → 漏**。自洽全过；顺序无关的正向比对在 1 mm 容差下也漏（仅差 0.47 mm）。
3. **RC-7 双重缩放 ×1.2 → 漏**。相似变换：所有比例、对称、长宽比、段数都不变；只有**绝对尺度**或精确基线能抓。若校验器只做"内库长宽比 ≈ 2:1"这类相对检查 → 漏。
4. **RC-3b 细微 captureRadius（差值 0.74 mm）→ 漏**。量级合理、为正、比 openingRadius 小——纯自洽检查看不出来；须靠 `opening−radius−0.002` 派生关系或精确基线。
5. **RC-1 1 mm 端点偏移 → 自洽检查可能漏**（若校验器**不含**"rail 组内段连续性 `b[i]==a[i+1]`"）——1 mm 偏移会让链在端点处断开；**能把这条抓回**的正是结构性连续性检查。

⇒ **给 D2-T02B 的硬性建议**：校验器必须同时含 **①索引对齐逐点基线比对（1e-5）**、**②手性/绕向（C3/C4）**、**③rail 组链连续性**、**④派生关系（capture 公式、宽度=点距、opening=inscribed）**、**⑤绝对尺度**。任缺一项，上表中就有一类错误成漏网之鱼。
