## 3. 【硬性要求】自证非空转 —— 4 个反向用例实跑观察 FAIL

命令：`PY Docs/Tools/check_generated_artifacts.py --self-test`
（方法：复制构件到临时目录 → 注入漂移 → 运行守卫 → 观察 FAIL → 复原。**只读原物**。）

**真实输出**：

| 反向用例 | 观察到的状态 | 明细 |
| --- | --- | --- |
| RC-B1 篡改 json 字段 parsedSegments 82→81 | **FAIL** | `B 类内容重算发现 1 处不符` / `check1_dataLanding.parsedSegments: 提交=81 重算=82` |
| RC-A1 伪造 TableConfig.asset 源 sha | **FAIL** | `源指纹不一致` / `asset记录=000…000` `入库副本=ba60fc20…` `F:原始=ba60fc20…` |
| RC-A2 改生成器源码（逻辑变/戳不变） | **FAIL** | `生成器逻辑已变：…/TableDataImporter.cs（台账 19c6b8320f3b05ea → 现 3aea3c38eccee159）` / `受影响生成物：…/TableConfig.asset` |
| RC-A3 篡改 baseline 字段 ball_radius | **FAIL** | `baseline 与重算不符 1 处` / `$.table.ball_radius: 提交=0.03 重算=0.028575` |
| **CLEAN 未篡改（阴性对照）** | **PASS** | `基线 FAIL={G3,G5}` = `现 FAIL={G3,G5}`（一致 ⇒ 篡改全部被复原、无残留） |

```
自证通过：每条守卫在注入漂移时都观察到了 FAIL，未篡改时 PASS。
```

> **阴性对照的稳健做法**：不与"全 PASS"比，而与**同一镜像未篡改时的 FAIL 集合**比。
> 原因：本仓库**此刻本就因上游变动而 G3/G5 FAIL**（见 §5），所以"全 PASS"不是正确的阴性期望；
> 正确期望是"篡改被复原后，FAIL 集合回到基线"。这避免了把**既有上游变动**误判成"守卫出现假阳性"。
⇒ **B 类（G1）、A 源指纹（G2）、A 逻辑指纹（G3）、A 内容（G4）均已被证明"能失败"**，即非空转。

> 过程留痕：自证 harness 首版有**延迟执行顺序 bug**（restore 在 tamper 之前跑），导致阴性对照误报 FAIL。已修（改为"篡改→跑→复原"立即执行）。**记录此事，因它与本轮"看起来对的错误"同族。**

- **G3 FAIL**：`TableIntegrityValidator.cs` 被改（Day 3 进行中）⇒ **它的产物 `day2-verification.json` 需重新生成/复核**。属**上游逻辑变动**，是 G3 正常工作。

**⇒ 未发现任何"产物与其生成器漂移"的活体损坏。** 两处 FAIL 是"上游动了"，正确处理是**重新生成 + 刷新快照 + 复核**，而非改动产物。

## 6. 未覆盖盲区（诚实清单）

1. **需 Unity 才能重算的内容**：`TableConfig.asset` 的**内容**、`day1/2/3-verification.json`、`day2-axis-probe.json`、`d2t02b-mesh-audit.json` —— 本轮只做**文件层**（源 sha + 逻辑指纹）。Unity 侧重生成入口**留 hook**（本轮未跑 Unity，按 team-lead 要求）。
2. **G1/G1b 的同源自洽性**：重算复用同一 FBX/PNG 解析实现 ⇒ 若解析器本身有系统偏差，**两侧同错**，一致性判据发现不了（需第三方库交叉，未做）。
3. **G3 假阳性**：改注释/格式也触发。
4. **float 精度**：0.1% 相对容差，低于记录精度的漂移不可辨。
5. **台账维护风险**：台账被顺手刷新则 G3 失效（需人工审查后刷新）。
6. **G5 噪声**：开发期持续变动会持续 FAIL，需人工判断"是合理变动还是异常"。
