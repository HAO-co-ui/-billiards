## 1. 架构分层与依赖方向

### 1.1 程序集与依赖方向（**无倒挂** ✅）

| 程序集 | 平台 | 引用 | 判定 |
| --- | --- | --- | --- |
| `Billiards.Runtime` | **全平台**（`includePlatforms: []`） | `Unity.InputSystem` | 玩家构建会包含它的**全部**内容 |
| `Billiards.Editor` | Editor | `Billiards.Runtime`, `Unity.InputSystem` | ✅ 方向正确 |
| `Billiards.Tests.EditMode` | Editor | `Billiards.Runtime`, TestRunner ×2 | ✅ 方向正确 |

**依赖方向检查结论**：Runtime **不**引用 Editor ✓；Editor → Runtime ✓；Tests → Runtime ✓。**没有倒挂。**

### 1.2 ★ 核心缺陷：Runtime 混入 Editor/Test 专用代码（**B-** 的来源）

**实测消费者清单**（我逐个 grep 了全仓引用）：

| 文件 | 行数 | 消费者 | 运行时消费者 |
| --- | --- | --- | --- |
| `Runtime/Table/TableReference.cs` | **386** | `Editor/TableImport/TableDataImporter.cs`、`TableIntegrityValidator.cs`、`Tests/…/D2T02B_IndependentAuditTests.cs`、`TableConfigTests.cs` | **0** |
| `Runtime/Core/MeshAlignmentMetrics.cs` | **281** | `Editor/TableImport/TableIntegrityValidator.cs`、`Tests/…/MeshAlignmentSensitivityTests.cs` | **0** |
| 合计 | **667 / 1118 = 59.7%** | — | **0** |

⇒ **团队负责人的怀疑成立**：Runtime 里 **667 行（60%）不是运行时资产**，却因 `includePlatforms: []`
**全部进玩家构建**。

**定性：这是分层违规，不是风格问题。** 两个文件的内容（JSON DTO、网格度量）**只在导入/校验时使用**，
把它们放进 Runtime 使"程序集边界"不再表达"运行时契约"。

**要注意的历史成因（不是"随手放错"）**：
`MeshAlignmentMetrics` 是我在 R1e 里**有意**放进 Runtime 的 —— 目的是让 **Editor 校验器与 EditMode 测试共用同一实现**
（当时是为了消除"校验器与测试各有一份几何实现"的口径分叉，见铁律 16）。
**动机是对的，落点选错了**：共享应当通过"**Editor-only 共享程序集**"，而不是"塞进 Runtime"。

**建议修法（不改 schema、不改逻辑，只动归属）**：
- 新建 **`Billiards.EditorOnly`** 程序集（`includePlatforms: ["Editor"]`），承载 `TableReference.cs` 与 `MeshAlignmentMetrics.cs`；
- `Billiards.Editor` 引用它；`Billiards.Tests.EditMode` **追加引用它**（这是关键的一步，否则测试编译不过）；
- `Billiards.Runtime` 只留：`PoolConstants`、`PoolGeometry`、`TableConfig`（**451 行**，全部是真正的运行时资产）。
- 成本：**移动 2 个文件 + 改 2 个 asmdef**。**必须在 Day 4 玩法代码落笔之前做。**

### 1.3 命名空间与程序集名不一致（低）

- 程序集 `Billiards.Editor` ↔ `rootNamespace: "Billiards.EditorTools"`（`Billiards.Editor.asmdef`）
- **有正当理由**：命名空间若叫 `Billiards.Editor`，会与 `UnityEditor.Editor` 在 `using` 上产生歧义。
- **问题不是这个选择，而是它没有被记录**。建议在 asmdef 旁或 ADR 里加一句理由，否则后来者会"顺手改一致"。

### 1.4 这套分层够不够支撑 Day 4–17？

| 未来的层 | 当前是否具备承载条件 |
| --- | --- |
| 物理内核（Day 4–7） | ✅ 具备。`Billiards.Runtime` + 计划中的 `Billiards.Physics` 全在 Runtime，纯 C#、可测 |
| 表现/视图（Day 8+，MonoBehaviour） | ⚠️ **缺一层**。目前只有 `Runtime`/`Editor`/`Tests` 三个程序集，没有"**玩法运行时**"与"**视图**"的区分。建议 Day 8 前补 `Billiards.Gameplay`（含 MonoBehaviour）与 `Billiards.View`，否则物理内核会与 MonoBehaviour 混进同一个程序集，**失去"物理层可离线测试"这个最大优势** |

### 2.2 分级判断（**不一律判死**）

关键事实：**这个工程虽然缺常规工装，但有更强的替代机制**，而且是**实测过、有证据**的：

| 替代机制 | 证据 |
| --- | --- |
| **离线编译门**（dotnet 直编全部 22 个 .cs） | 每轮都跑，**0 warning / 0 error**；且我实测过它能提前拦住 Unity 往返（R2/R3 各拦 1 次编译错误） |
| **断言测试** | **53 个** EditMode 测试，含**负对照**（`MeshAlignmentSensitivityTests` 钉住"面点度量对位移盲"）与**证伪测试**（`ModelOrientationTests` 证明"翻转朝向常量会 FAIL"） |
| **可判据验收器** | Day 1 **26 项**、Day 2 **33 项**、Day 3 **22 项**，全部 `expected/actual/detail` + 退出码 |
| **独立复核** | `Docs/Reviews/` **9 篇**，含数值重算、判别力审计、归纳闭合性 |
| **墓碑与勘误** | 被证伪的结论**不留主张、只留证伪结论 + 指针** |

⇒ **判定：B（可接受，但应在 Day 4 开工前补最小集）。**

**理由**：对"3 天、7000 行、0 玩法代码"的基建期，CI/分析器缺失的**风险敞口有限**（没人并行提交、无外部贡献者）；
而**替代机制的强度高于同阶段大多数工作室**。但 Day 4 开始写玩法后，行数会快速上升，
**届时"无 CI、无 warnings-as-errors"就会从"可接受"变成"真缺口"**。

**最小集（Day 4 前，成本 <1 h）**：
1. `.editorconfig`（缩进/换行/`csharp_new_line_before_open_brace` 等基础项，与现有风格一致即可，**不建议引入 200 条规则**）
2. 一个 CI 或本地脚本：**编译（0 警告） + `-runTests EditMode`**，失败即红
3. 把已有的**离线编译预验证**固化成脚本（现在是我每次手写 dotnet 命令 —— **这是隐性知识**）

| --- | --- |
| **确定性** | ✅ **明确加分**。无 Unity 生命周期耦合、无隐式 `Time.deltaTime`、无执行顺序不确定。Day 4 的 T9（逐位一致）**只有在纯 C# 下才可能成立** |

## 5. 性能与平台意识

### 5.1 运行时分配（✅ 零分配）

| 文件 | 分配行为 | 判定 |
| --- | --- | --- |
| `PoolGeometry.cs`（172 行） | 纯静态、无状态、无 `new`、无 LINQ | ✅ **零分配** |
| `PoolConstants.cs`（102） | 纯 `const` | ✅ |
| `TableConfig.cs`（177） | SO 数据 + `ConsistencyErrors()`（仅调用时分配 List，非热路径） | ✅ |

⇒ **真正的运行时表面（451 行）是零分配的** —— 这是 A 级表现。

### 5.2 Editor 侧分配（不影响帧率，但有 1 处结构含义）

- `MeshAlignmentMetrics` 构造会建**3 个 Dictionary + 多个 List + 2 个数组**（10572 顶点 / 19954 三角，`TableIntegrityValidator.cs:835` 用 `ToArray()` 各拷一次）
- 这在 Editor/测试里**可接受**，但**这正是它绝不该留在 Runtime 的第二个理由**：
  **一旦有人在运行时 `new MeshAlignmentMetrics(...)`，就是一次性大分配 + 长期占用**。

### 5.3 Day 4 求解量（**无瓶颈**，给数）

| 量 | 计算 | 值 |
| --- | --- | --- |
| 每固定步 TOI 次数 | 82 段 × 16 球 × 3 子步 | **3,936** |
| 每秒（120 Hz） | 3936 × 120 | **472,320 /s** |
| 最坏（16 次迭代全用满） | 472,320 × 16 | **7.56 M /s** |

每次 TOI 是"点-线段最近点 + 一元二次求根"，约几十 flops ⇒ **O(10⁷) flops/s 量级**。
对比：现代桌面 CPU 单核 ~10¹⁰ flops/s ⇒ **占用 < 0.1% 单核**。
⇒ **Day 4 spec 的 82×16×子步 求解没有性能瓶颈**；`MaxToiIterations = 16` 的守卫成本也可忽略。

### 5.4 平台意识

- 目标 PC 60 fps；`FixedDeltaTime = 1/120`（spec §3）—— **固定步进不随帧率变化** ✓ 与 60 fps 渲染解耦 ✓
- `float` 精度：`PoolConstants.cs:15-18` 已论证（1.27 m 处分辨率 ~0.12 µm，远优于球半径）✓
- ⚠️ **无 `Application.targetFrameRate` / VSync 设置**（Day 3 场景未设）—— Day 15 调优项，非当前缺陷

### 8.2 缺口清单（4 条，按严重度）

#### G-0 【新】两份实现**已经分叉**（铁律 16 的第三次实例）· 严重度：中高

团队负责人问"二者会不会漂移" —— **实测：不是"会不会"，是"已经分了"**：

| **扫描对象** | **固定路径** `MainScenePath` | **当前活动场景**（`scene` 局部变量） |
| 取场景方式 | `EditorSceneManager.OpenScene(MainScenePath, Additive)` | `SceneManager.GetActiveScene()`（不符才 `OpenScene(Single)`） |
| 计数实现 | **独立私有方法** `CountRigidbodiesInScene(string)` | **16 行内联循环**重复同一逻辑 |
| 判据表达式 | `rigidbodyCount == 0` | `rigidbodies == 0`（**表达式一致**） |
| 场景缺失兜底 | **有**（`mainScene == null` → FAIL「无法检查」） | **无** |
| `detail` 文案 | 有（「台球运动全部由自研…」） | 无 |

⇒ **判据表达式逐字一致，但实现、取场景方式、兜底、文案都不同** ——
即"同一不变量两份独立实现"。目前已观测到的**行为差异**：
- `SCN-04` 固定扫 `Main.unity`；`SCN-06` 扫**当前活动场景** ⇒ 若 Day 3 验证时活动场景不是 `Main.unity`，`SCN-06` 会**扫错对象**。
  目前之所以安全，是因为 `Day3Validator.VerifyScene` 会先确保打开 `Main.unity` —— **这是巧合（调用顺序的副作用），不是设计**。

**这与 R3 的 `ValidateInteractive` vs `RebuildAndValidateInteractive` 是同一族缺陷**：同一逻辑两处实现。
R3 的修法是"单点 helper"（铁律 16），**这里适用同一修法**。

#### G-1 守卫**只扫场景，不扫 prefab** · 严重度：**高**

实测 **18 个 prefab**（`Ball_00..15`、`BallPrefab`、`PoolCue`）**全部未被任何检查覆盖**。
**Day 4/5 正是从这些 prefab 实例化球**：一个 `Rigidbody` 挂在球 prefab 上 ⇒ 每次实例化都带 PhysX 刚体 ⇒
**静默破坏确定性**，而 `SCN-04`/`SCN-06` **仍全绿**。

#### G-2 无**代码级**禁止 · 严重度：中（**但实测当前是干净的**）

团队负责人要求核实 `Physics.` 实际调用数。**实测全工程 = 2 处**：

| 位置 | 调用 | 性质 |
| --- | --- | --- |
| `BilliardsProjectSetup.cs:210` | `Physics.IgnoreLayerCollision(...)` | **写**（建立隔离） |
| `BilliardsProjectVerifier.cs:106` | `Physics.GetIgnoreLayerCollision(a, b)` | **读**（验证隔离） |

⇒ **两处都是"守卫机制本身"，全工程没有任何"玩法性质的 PhysX 调用"** ✅
（**不存在** `Physics.Raycast` 之类的误用 —— 团队负责人举的那个例子目前**没有发生**。）

**但缺口仍然成立**：没有机制**阻止将来**有人为实现瞄准射线写 `Physics.Raycast` ——
那不新增任何 `Rigidbody`，`SCN-04`/`SCN-06` **抓不到**，却引入运行时 PhysX 依赖。
⇒ **守卫只拦"结果"，不拦"来源"。**

#### G-3 守卫**自身依赖 PhysX 模块** · 严重度：中（且是 G-1/G-2 之外的独立事实）

`Physics.IgnoreLayerCollision` / `GetIgnoreLayerCollision` **需要 `com.unity.modules.physics`**，而它**仍在 manifest**（`physics2d` 也在）。
⇒ 形成了**耦合链**：

即：**「禁用 PhysX」的实现方式是"调用 PhysX 来禁用它"，而这正好锁死了"把 PhysX 从构建里剔除"这条路。**

#### G-4 【最重】守卫**不会被自动执行** · 严重度：**高**

## 11. 错误模式登记（本工程值得防范的）

> 本节是本次审计的**方法学产出**，不只针对本次。团队负责人要求把下面第 1 条登记在案。

### 11.1 【登记】用片面检索支撑**全称否定**命题

**发生**：团队负责人在本任务派单里断言「这条铁律目前**没有任何守卫**，只靠自律」，依据是
`grep -rn "PhysX|Rigidbody" Assets/_Project/Tests` **命中 0**。

**为什么错**：`Tests/` 下确为 0（数字对），但**结论是"全工程无机制"**，而机制在 `Assets/_Project/Scripts/Editor/` 下。
⇒ **一个局部范围上的空结果，被当成了全称否定命题的证据。**

**它属于哪一族**：与团队已登记的错误同族 ——
- 铁律 17「**计数 ≠ 语义**」（用 grep 计数判断"未清除"，而实际是墓碑）；
- 本工程历史上的「**检查测了一个"方便测的量"，而不是"真正需要成立的那个量"**」。

三条的共同点：**用一个容易获得的量，去支撑一个它支撑不了的结论。**

**防范规则（建议入铁律）**：
> **全称否定命题（"没有 X"）必须给出检索空间的定义，并证明该空间是完备的。**
> 只在一个子目录里 grep 到 0，**不能**推出"全工程没有"。
> 正确表述要么限定范围（"`Tests/` 下 0 处"），要么先枚举检索空间（"工程内所有 `.cs` 的分布见 §0"）再给结论。

**本次审计自身的对照**：我在 §0 先给出了**全工程按目录的行数与文件清单**（作为检索空间），
再逐条给否定/肯定结论 —— **这正是该规则要求的做法**。

### 11.2 本工程已登记的同类错误（供交叉参考）

| # | 错误模式 | 出处 | 修法 |
| --- | --- | --- | --- |
| 1 | 用片面检索支撑全称否定 | 本文 §11.1 | 先定义检索空间 |
