| 项 | 值 |

| 适用 | 本工程全部 C# 代码、资产管线脚本、验收器与测试 |

## 1. 程序集边界（分层）

| 程序集 | 平台 | 允许引用 | 内容 |
| --- | --- | --- | --- |
| `Billiards.Runtime` | **全平台** | `Unity.InputSystem` | 只有**玩家运行时会用到**的东西：`PoolConstants` / `PoolGeometry` / `TableConfig` |
| `Billiards.Diagnostics` | **Editor** | *（无）* | **只在导入/校验/测试时用**的东西：`TableReference`(DTO+比对) / `MeshAlignmentMetrics` / `MeshAlignmentTolerances` / `PhysicsBanAudit` |
| `Billiards.Editor` | Editor | Runtime, Diagnostics, `Unity.InputSystem` | 菜单 / 导入器 / 验收器 |
| `Billiards.Tests.EditMode` | Editor | Runtime, Diagnostics, TestRunner×2 | EditMode 测试 |

**R1-1** 依赖方向只能 `Editor/Diagnostics/Tests → Runtime` 与 `Editor/Tests → Diagnostics`。
**不得**出现 `Runtime → Editor/Diagnostics`，不得有任何循环。
- **验证**：`grep -rn "^using Billiards" Assets/_Project --include=*.cs` 逐条核对；或看 asmdef `references`。
- **违反示例**：`Runtime/Core/PoolGeometry.cs` 里 `using Billiards.Diagnostics;`

**R1-2** **Runtime 里不得放"玩家构建不会用到"的代码**。
- **验证**：对 Runtime 下每个 public 类型，`grep` 全仓引用，然后回答一个**明确的问题**：
  **这个类型会被"玩家构建里的代码路径"用到吗？** —— 而**不是**"它现在有没有消费者"。
- **两个方向的误判都要避免**：
  - **现在有消费者、但只被 Editor/Tests 消费** ⇒ 不该在 Runtime。
    违反示例：`MeshAlignmentMetrics` 放回 `Runtime/Core/`（整改前实测 Runtime 1118 行里
    **667 行（60%）** 属此类，会被编进玩家构建）。
  - **现在零消费者、但属于运行时基础** ⇒ **必须在 Runtime**。
    示例：`PoolConstants`、`PoolGeometry` —— 它们 Day 4 才被物理内核用上，当前**零运行时消费者**。
    **纯 grep 计数会把它们错判为"该移走"**。
- ⇒ **本规则不能用纯 grep 自动化**：判定依据是**用途**，`grep` 只作辅助。
  这也是它没有配上自动守卫、而列在此处供评审对照的原因。

**R1-3** 命名空间与程序集**同名**。
- **现状（4 个程序集，含全部例外 —— 逐一列出，不只记一个）**：

  | 程序集 | 命名空间 | 同名？ |
  | --- | --- | --- |
  | `Billiards.Diagnostics` | `Billiards.Diagnostics` | ✅ **同名** |
  | `Billiards.Runtime` | `Billiards`（+ 子命名空间 `Billiards.Core` / `Billiards.Table`） | ❌ 作前缀 |
  | `Billiards.Editor` | `Billiards.EditorTools` | ❌ **刻意例外** |
  | `Billiards.Tests.EditMode` | `Billiards.Tests` | ❌ 作前缀 |

- **例外理由（逐条，均为刻意保留，不是疏漏）**：
  - `Billiards.Editor` → `Billiards.EditorTools`：命名空间若叫 `Billiards.Editor`，会与
    `UnityEditor.Editor` 在 `using` 处产生**歧义**。
  - `Billiards.Runtime` → `Billiards`：根命名空间作**前缀**，允许按层细分
    （`Core` / `Table` / 未来的 `Physics`）；与 asmdef 的 `rootNamespace` 一致。
  - `Billiards.Tests.EditMode` → `Billiards.Tests`：测试程序集按**平台**细分
    （将来会有 `Tests.PlayMode`），命名空间不必随之分裂。
- **改动任一例外前须评估全部 IDE 提示与 `using` 歧义。**

**R1-3a（R1-3 的已知成本）** 凡在 `Billiards.*` 内调用**与任一 `Billiards.*` 嵌套命名空间同名**的 Unity API，
**必须全限定**。

- **当前已知**：`Physics`。`Billiards.Physics`（Day 4 spec 硬要求，**不可改名**）会遮蔽 `UnityEngine.Physics` ——
  C# 名字查找**先逐层查外层命名空间、命中即停**，这一步**早于 `using` 指令**。
- **已发生（实例）**：`BilliardsProjectSetup.cs` 与 `BilliardsProjectVerifier.cs` 各有一处裸 `Physics.…`
  因此 CS0234，已改为全限定。**行为不变**（仍是 Unity 的层隔离 API）。
- **同源风险**：若将来把 `Billiards.EditorTools` 改名成 `Billiards.Editor`，
  **裸 `Editor` 同样会遮蔽 `UnityEditor.Editor`** —— 这是 R1-3 例外条款存在的**第二个**理由。
- **验证**：`grep -rnE "[^.a-zA-Z]Physics\." Assets/_Project --include=*.cs | grep -vE ":[0-9]+:\s*//"` 应**无命中**。
- **为何验证式必须排除注释行**：注释里**讨论**该遮蔽时会合法地出现裸写法（例如"不要写 `Physics.Raycast`"）。
  本工程已有"规则被自己的 doc 注释判红"的实际先例，故验证式一律排除注释。

**R1-4** 程序集归属由**自动守卫**守住（见 R4-2），不靠评审时的记忆。

## 2. 命名与风格

**R2-1** 风格以 `.editorconfig` 为准（缩进 4/空格、LF、UTF-8、Allman 大括号、`System` using 在前）。
**R2-2** 命名：常量/公有成员/类型 → `PascalCase`；局部变量/参数 → `camelCase`；私有静态字段 → `_camelCase`；接口 → `IPascalCase`。
**R2-3** **Unity 序列化字段保留 `public` 字段**（不改属性）—— Unity 序列化不认自动属性。
**R2-4** 禁止无意义缩写（`Mgr`/`Cfg`/`Svc`）。领域缩写（`URP`/`GDD`/`TOI`/`FBX`）可用。
- **验证**：`.editorconfig` + `dotnet format --verify-no-changes`（有 dotnet 环境时）。

## 3. 测试要求

**R3-1** **每个实现任务必须自带"负路径"测试** —— 至少 1 条**能失败**的用例，证明主判据不是恒真。
- **验证**：新任务的测试文件里找"注入/翻转/变异"类用例（如 `Falsification_*`、`*_Negative*`、注入错位）。
- **违反示例**：只有 `Assert.Pass`（恒真）；或期望值由**被测常量自身**导出（近代数恒等式，改 ±1e-4 仍通过）。

**R3-2** **禁止恒真断言**。任何"永远通过"的检查都不得进入测试或验收器。
- **验证**：审读断言；或按审计方法"把输入改到明显错，看它是否失败"。
- **违反示例（已修）**：`PoolConstantsTests.TableTestAssembly_IsWired` 曾用 `Assert.Pass`。

**R3-3** **否证性结论必须双重验证**（"什么也没找到"本身就是否定性结论预期输出的样子）。
- **验证**：给出检索空间的定义 + 第二种检索方法。

**R3-4** 断言优先用**可判据数值**（`expected`/`actual`/容差），不用"看起来对"。
**R3-5** 测试**不得产生仓库改动**（不写 `Assets/`、不改已提交证据）；输出走仓库外或 `-outputDir`。

**R3-6** **报测试数必须带修订锚点**，格式 `<通过数>/<总数> @ <提交短哈希 或 "工作区">`。
- **不得只写「72/72 全绿」** —— **不带锚点的数字不得被引用为当前状态**。
- **权威数字由复核方在冻结修订上测得** —— **不由各人各自在漂移的工作区上测**。
- **适用**：EditMode / PlayMode 测试数、三个验收器的通过数、以及任何"我跑了、通过了"的**计数型**断言。
- **为什么**：`58` / `66` / `72` 三个数字都曾被称为"全绿"，却**对应三个不同修订**（期间有多人各自加用例）
  —— 不标修订地引用，复核方会把过期数字当有效。**本轮由两名 worker 各自独立发现同一坑，故制度化，不靠自觉。**
- **验收器时效规则**：某验收器的**自身源文件**被改动后，其此前结果**即告过期** ——
  **哪怕改动看起来"构造上等价"**（实例：Day1 的 `BilliardsProjectSetup.cs` / `BilliardsProjectVerifier.cs`
  被全限定改动后，Day1 的旧结果过期）。
- **规矩与状态分离**：**本文件只放规矩**；当前各修订的实测数字、分文件构成、验收器时效状态，
  一律见 `Docs/测试数基线台账.md`（避免两处各写一份而分叉）。

**R3-7** **测试可以产出证据，但必须满足两个条件**（V-6 豁免条款，来自 Day 4 切片 C）。
- **允许**：测试把结构化证据写到 `Docs/Reports/**`（先例：`d2t02b-crosscheck.json`、`d4-segment-coverage.json`），
  但必须 ① 经 `ReportOutput.ResolveReportPath` 一类**支持 `-outputDir` 的单点**输出，
  ② 产物**入库为证据**（不是临时垃圾）。
- **判据**：不满足这两条的测试写盘视为违规。
- **为什么**：验收器（`DayNValidator`）与测试的分工是"**谁判定、谁记录**"——
  但有些证据只有测试跑得出（如 1230 次逐段扫描），强行搬进验收器会让验收器承担仿真负担。
  ⇒ 用这条豁免把"允许"与"随意写盘"分开。

**R3-8** **JSON / 机器可读输出里的数值，一律显式 `ToString(InvariantCulture)`**（V-7，来自 Day 4 切片 C）。
- **现象（实测）**：Unity 里 `StringBuilder.Append($"...{x:F5}...")` 的**内插格式说明符不生效** ——
  原样输出字面量 `F5`，使 JSON 非法（切片 C 因此拿到过一次 JSON 解析失败）。
- **规则**：机器可读输出中的数值不要依赖内插格式说明符；一律
  `x.ToString("F5", CultureInfo.InvariantCulture)` 之类**显式调用**。
- **另一个理由**：`InvariantCulture` 同时挡掉"不同区域设置下小数点变逗号"这一类静默损坏。

## 4. 守卫（Guard）的形态

**R4-1** **同一不变量的检查必须单点实现**（铁律 16）。
- **验证**：`grep` 该判据的核心表达式（如 `GetComponentsInChildren<Rigidbody>`），**应只在 1 个文件里出现**。
- **违反示例（已修）**：`SCN-04`（Day 1）与 `SCN-06`（Day 3）曾各写一份 Rigidbody 统计，且**已分叉**。
- **本工程已发生 3 次**（R3 两入口前置条件、R3 报告路径解析、SCN-04/06）⇒ 列为**架构评审固定检查项**：
  凡新增检查/守卫，先问「**同一个不变量还有没有别处在实现它？**」

**R4-2** **守卫优先进测试套件**（铁律 18）—— 因为本工程**没有 CI**，"验收器里的守卫"= 没人点菜单就不跑。
- **验证**：该守卫是否出现在 `Docs/Reports/*editmode-tests.xml` 的用例列表里（而不是只在验收器报告里）。
- **违反示例（已修）**：物理铁律原先只在 `SCN-04`/`SCN-06` 里，`-runTests` **完全不覆盖**。

**R4-3** 守卫必须带**非空转证据**：断言"扫到了 N 个对象"（N>0），否则"0 个违规"可能只是"0 个被扫"。
- **验证**：守卫输出里有 `scene=1 prefab=18` 这类计数，且有断言下限。
- **违反示例（已防）**：只断言 `RigidbodyCount == 0` 而不检查是否扫到文件。

**R4-4** 守卫触发**不得静默**：要么 FAIL，要么计成可断言的计数器。
**R4-5** **不得以删除检查作为让套件变绿的手段**（铁律 4）。

## 5. 架构铁律

**R5-1** **自研二维定长步进物理，禁止 Unity PhysX。** 球桌/球杆物理不得使用 `Rigidbody`/`Collider`；
运行时程序集不得引用 `UnityEngine.PhysicsModule`。
- **验证**（三条，缺一不可）：
  1. `PhysicsBanGuardTests.ScenesAndPrefabs_ContainNoRigidbodyOrCollider`（场景 + prefab，自动执行）；
  2. `PhysicsBanGuardTests.RuntimeAssembly_DoesNotReferencePhysXModule`（代码级，拦"来源"）；
  3. `SCN-04`/`SCN-06`（验收器侧，与 1 共用 `PhysicsBanAudit`）。
- **注意**：守卫的实现本身用到了 `Physics.IgnoreLayerCollision`（层隔离），**因此 Player 构建目前仍带 PhysX 模块**。
  去耦合方案（写 `DynamicsManager.asset` 而非调 API）见 D4-AUDIT-01 §8.3-⑤，**排在发布前**。

**R5-2** **坐标转换只允许一处**：`PoolGeometry`（见 ADR-0001）。场景/预制件不得对模型叠加手动旋转。
**R5-3** **确定性**：物理层不引 `Time.deltaTime` / `UnityEngine.Random` / 无序容器迭代序；开方/三角走单一口径。
**R5-4** 校验/生成**入口不得重建被校验对象**：产物缺失才生成，存在则只校验（否则只证明"生成器自洽"）。

### 9.3 **未改**的东西及理由（防后来者"顺手补改"而踩坏）

| 项 | 处置 | 理由 |

| **检查项 ID**：`D4-PHY-01` / `D4-SCN-01` / `D4-SCN-02` / `D4-BAN-01` / `D4-BLD-01` / `SCN-0x` / `LYR-0x` / `RUN-01` | **保留原样** | 它们是**已入库证据 JSON 的键**（`Docs/Reports/*.json` 里逐字出现）⇒ 改名即**作废全部已入库证据**。它们是**标识符，不是时间**。 |
