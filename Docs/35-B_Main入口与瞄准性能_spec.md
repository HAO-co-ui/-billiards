## 1. 任务①：`Main.unity` 成为正式游戏入口

### 1.1 现状（改前）与病根

- `Main.unity` 改前是**空壳**（1 个 `MeshRenderer` + 1 个 `Camera` + 1 个 `Light`、**0 个 MonoBehaviour**）⇒
  用它出包 = **黑屏死包**。
- 出包入口因此一度被迫改用灰盒场景（`PerformanceSetup` / `BuildWindows` 指向 `PhysicsGreybox.unity`），
  代价是**与 `SCN-02`（Day1）与 `D4-BLD-01`（Day4）互斥** —— 那两条断言**提交态 build list 恰好是
  `[Main.unity]`**，而 `BilliardsProjectSetup.Apply` 每次又把它写回 `Main.unity` ⇒ "谁后跑谁生效"。

### 1.2 改法（as-built）

**唯一实现点**：`GreyboxSceneSetup` 新增

| 成员 | 作用 |
| --- | --- |
| `MainScenePath` | `Assets/_Project/Scenes/Main.unity` |
| `MainGameplayRootName` = `GameplayLayer` | 玩法层根对象名，**同时是幂等标记** |
| `AttachMainGameplayLayer(Scene)` | **把玩法层叠加到既有 Main**（复用桌/地面/相机/光；见下） |
| `ApplyMainScene()` | **幂等**：`MainHasGameplayLayer()` 为真 ⇒ **早退不写盘** |
| `RebuildMainScene()` | 强制：打开 Main → 回收旧玩法层 → 重新叠加 → 保存 |
| `BuildGameplayHosts(...)` | **玩法层宿主的唯一构建点**（灰盒与 Main **共用**，铁律 16） |
| `BuildFromCommandLine/RebuildMainFromCommandLine` 等 | `-executeMethod` 入口 |

`AttachMainGameplayLayer` 的四步：
1. 复用既有 `PlayfieldRoot` 与名为 `Main Camera` 的相机；
2. 给相机**缺失才补** `AudioListener` / `CameraViewportFitter`（**绝不新增第二台相机 / 第二个监听器**）；
3. 回收并重建球可视物（白球 + `RackBall_1..15`），挂**既有** `PlayfieldRoot` 下；
4. 在 `GameplayLayer` 根下建全部玩法宿主（调试叠加层**关**）。

同时把原 `BuildScene()`（灰盒）**重构成调用同一个 `BuildGameplayHosts`**（相机在建玩法层之前建好），
并把 `MaterialVisualSetup.BuildScene()` 的末尾接上 `AttachMainGameplayLayer(scene)` ——
**保证两条写入路径都产出完整 Main**（否则"Build Materials, Scene & Prefabs"会把玩法层洗掉）。

**出包口径统一**：`PerformanceSetup.BuildScenePath`（原 `GreyboxScenePath`）与 `BuildWindows` 均指向
`Main.unity`；`T120 ③` 由"断言灰盒场景非空壳"改回**断言 `Main.unity` 非空壳**（含驱动器 / HUD / 瞄准辅助）。
⇒ 互斥的根因（"Main 是空壳"）消除，`SCN-02` / `D4-BLD-01` **变成真正正确**。

## 3. 任务③：拖动瞄准的卡顿

### 3.1 三处成本（改前）

1. `AimAssistController.Fingerprint`：每帧对 17 球 × 4 个 float 走 `ToString("R") + StringBuilder`；
2. `RefreshPrediction`：拖动时指纹每帧都变 ⇒ **每帧**跑一次 `ShotPredictor.Predict`（最多 **240 步**）；
3. `AimAssistView`：每帧 `new List` + 每段各建一个列表；且**逐路径取样点**铺虚线
   （每段至少 1 段 ⇒ ~240 个 `LineRenderer`）。

### 3.2 改法（as-built）

| 位置 | 改动 |
| --- | --- |
| `AimAssistController` | 指纹改 **64 位 FNV‑1a 数值哈希**（零分配、零字符串）；新增 **`ShouldRecompute` 纯函数**（前沿节流 + **尾沿强制**）；新增 `minRecomputeIntervalSeconds`（默认 `1/30` s）；用 **`ShotPredictionWorkspace`** 复用探测内核与缓冲 |
| `ShotPredictor` | 新增**带工作区**的重载（复用探测内核 + 快照 + 路径缓冲）；4 参旧重载**输出逐位不变**（内部新建一次性工作区） |
| `ShotPredictionWorkspace`（新） | 持有可复用探测内核 + 快照/路径缓冲；缓存键 = (桌, 参数, 三个标量)，不符即重建；复用路径**显式补一次 `ResetDiagnostics()`**（`LoadBalls` 不清每杆计数） |
| `AimAssistView` | 虚线段缓冲复用；新增 **`AppendPolylineDashSegments`**（**按弧长**铺虚线 ⇒ 段数只由路径总长决定）；**只在预测重算过（版本变化）时重绘** |

**硬约束（尾沿）**：`ShouldRecompute` 在"本帧指纹 == 上一帧指纹"（= 输入已停止变化）时**无条件返回 true**
⇒ **停止拖动后的下一帧必定是最新预测**，瞄准线不会停在旧值。

### 3.3 可测证据（新增冒烟模式）

`SmokeProbe` / `SmokeProbeRunner` 新增 **`-billiards-smoke-aim`**（无值标志）：采样期间**每帧连续改变瞄准角**
（`AimSweepDegrees(frame) = (frame × 4.5°) mod 360`）⇒ 逼出"预测重算"这条最坏路径。
运行时挂钩走 **Core 定义、Physics 实现**的接口 `ISmokeAimSweepTarget`（**不产生反向依赖**）。

`unity_batch.sh` 新增 `smoke-aim` 步骤。判定口径（**批次 B 已统一为严格**）：
- **静置**：**严格闸门**（`MeetsTarget`：均值 ≤ 16.67 ms、掉帧 ≤ 2%）—— **始终未改**；
- **拖动**：~~`MeetsDragTarget` 宽松闸门（均值 ≤ 50 ms、掉帧 ≤ 40%）~~ ⇒ **已删除**。

> **⚠ 口径变更（批次 B；前后两套数字 + "为什么当时必须有、为什么现在能删"）**
> | 时期 | 拖动闸门 | 拖动实测（同口径） | 说明 |
> | --- | --- | --- | --- |
> | 批次 A（内核未优化） | **宽松**：均值 ≤ 50 ms / 掉帧 ≤ 40% | **24.9 ms（40 fps）/ p95 76.3 / 掉帧 162** | 一次 240 步预测要**数十毫秒**（内核每子步**无条件**扫 `每球 × 全部 82 段`）⇒「60 fps 且掉帧 ≤ 2%」**结构上不可达**；沿用严格闸门只会**恒红**（等于没有判据）⇒ 当时**必须**放宽，且它**不声称 60 fps** |
> ⚠ **交叉引用（不删历史）**：本行是**当批次的历史基线**（当时拖动 40 fps）。该问题已由**批次 C** 修复，**现状**见 §12.2.2（拖动 `6.9442 ms` / 144 fps / 掉帧 0）。按纪律**保留最后已知良好证据**，不做替换式删改。
> | **批次 C 之后（现状）** | **严格**（与静置**同判** `MeetsTarget`） | **6.96 ms（143.8 fps）/ p95 6.97 / 掉帧 0** | 内核加了**保守包围盒预筛**（等价、逐位不变）⇒ 拖动**已达标** ⇒ **宽松闸门与其两个阈值常量一并删除**（**不留"已作废"的死闸门** —— 留着必被后人误用）。由 `T131 ⑤` 做**源码级 + 类型级**守卫：采样执行体**不得引用** `MeetsDragTarget`，且 `typeof(SmokeProbe).GetMethod("MeetsDragTarget")` **必须为 null** |

### 3.4 ⚠ 实测结论（如实，**这是本单最重要的发现**）

| 冒烟 | 均值 | p95 | 最大 | fps | 掉帧 | renderer | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 静置 600 帧 | 6.94 ms | 6.95 ms | 6.95 ms | **144** | 0 / 600 | **27** | ✅ 严格闸门通过 |
| **连续拖动瞄准 600 帧** | **24.9 ms** | **76.3 ms** | 83.4 ms | **40** | 162 / 600（27%） | **34** | ✅ 宽松闸门通过 |

- **旧盲带被关闭**：改前冒烟只测静置 ⇒ 拖动峰值**从未被测过**。现在它是**可判定**的。
- **残差归因（实测+推算）**：拖动帧的额外成本**主要来自预测重算本身**，不是渲染 ——
  证据：`AppendPolylineDashSegments` 把 `rendererCount` 从 **260 降到 34**（~7.6×），
  但均值只从 26.1 → 24.9 ms（~5%）⇒ 瓶颈不在渲染器。
  单次重算 ≈ 最多 **240 步** × 内核单步 ~0.37 ms（Day16 实测静止单步）≈ **数十毫秒**，
  与观测到的 p95 ~76 ms 同量级 ⇒ **内核固有成本**。
- ⇒ **拖动路径无法同时满足"60 fps 且掉帧 ≤ 2%"**（一次同步重算就吃掉数帧）—— 该"闸门"会**恒红**、
  等于没有判据。故拖动路径用**宽松闸门**（只拦量级失控），**不声称 60 fps**。

## 5. 盲带（如实）

1. **拖动帧率**：拖动瞄准 40 fps（均值 24.9 ms）**低于 60 fps**（⚠ **交叉引用（不删历史）**：该问题已由**批次 C** 修复，**现状**见 §12.2.2 —— 拖动 `6.9442 ms` / 144 fps / 掉帧 0；本行**保留**以存证当时基线）；达到 60 fps 需要**更廉价的预测模型**
   或**较短的拖动期步数上限**（后者是**可见**权衡：拖动中瞄准线变短、松手恢复全长）——**未实施，待裁定**。
2. **拖动期"卡顿"的主观观感**不由判据判定（`R3-4`）；本单只给出**帧时数字**。
3. **虚线段数变化**：按弧长铺虚线会改变虚线的**断点位置与段数**（观感略更"实"）；无自动判据覆盖
   "观感是否变差"（`T80` 只判"间隙 > 0 且 ≥ 屏幕可辨下限 + 段数闭式"，且那条测的是**单段**函数，未变）。
4. **`OnGUI` 实际绘制**不在 EditMode 可判范围（无渲染派发）⇒ `T129 ③/④` 只保证**结构**。
5. **无改前拖动基线**：拖动冒烟是**本单新增**的，因此**不存在**"改前 vs 改后"的同类数字
   （改前从未测过——这正是被关闭的盲带）；可对比的是 `rendererCount` 260 → 34（同一路径、两版之间）。
6. `MaterialVisualValidator` 的 **day3 渲染证据图**在跑验收器时会被覆写（改了 Main 的内容）⇒
   本单按纪律 `git checkout -- Docs/Reports/` 还原，**不把 day3 入库证据更新为本单版本**（待裁定）。

## 9.3 等价性论证（**与浮点精度无关**，故跨运行时成立）
**精确事实（ℝ）**：球心到线段距离 ≤ r ⇒ 取最近点 q（q 必落在段端点 AABB 内）⇒
`|p.x − q.x| ≤ r` 且 `|p.y − q.y| ≤ r` ⇒ `p.x ∈ [minX − r, maxX + r]`、`p.y ∈ [minY − r, maxY + r]`。
TOI 侧**同一推理**：接触 ⇒ 扫出 AABB 与 段AABB⊕r 相交。
⇒ 预筛盒 = **段AABB ⊕ (r + ε)** ⇒ 该蕴含**严格保留** ⇒ **被跳过的对必然不重叠 / 必然不接触**。
⇒ **ε 只吸收"构造预筛盒那几步加减"的舍入**（尺寸 ~1 m 时约 1e-7），取 **1e-6 > 2× 该界**
⇒ 即便按浮点最坏情况取值也不会误跳 ⇒ **结论跨 Mono / CoreCLR 同成立**。**全工程无"严格比较不留余量"写法。**

## 10.6 教训（写给后来者）
- **"绿而空"**：判据亮绿**不等于**证据有信息；**任何"只查存在/只查落盘"的判据都有这个洞**。
- **两个空洞判据会互相掩护**（一个只数文件、一个永不失败）⇒ 空洞被**两个**绿灯共同掩盖，且看起来"很正常"。
- **正解 = 事前拦截 + 两层同判**：判据内断言"非退化 / 有差异"，工具外每次刷新**自动**再查，且工具**自带自证**。
- **别让"存在"冒充"有内容"**：**文件大小下限 + `distinctColors > 1` + A/B 差异**，三者合起来才够。
- **源码级守卫要写【调用形态】（带 `();` 或完整语句），否则【定义】会让它恒真**。
  实例（本批 2 次，均由**注入自己**抓出）：① `g5-peaks` —— `Contains("SampleScenePeaks(")` 命中的是**方法定义**，删掉**调用**照样绿；
  ② 同型残留 —— `Contains("TotalPredictSteps")` 命中的是**属性声明**（与累计行同文件），删掉累计行 `TotalPredictSteps += …` 仍绿。
  ⇒ 一律改成**使用形态**（`"SampleScenePeaks();"` / `"TotalPredictSteps +="`）。这是本轮**第 4 次「绿而空」**，且是用**我们自己的注入协议**在自己代码上发现的。
- **清除残留引用前，先判「这句说的是不是同一条声称」**：**残留替换只对「同一声称」的引用执行**；
  先**分类**（**声称源头** / **已限定** / **只是巧合含相同词**）再决定改不改。
  反例：把「四张逐字节相同 · 1 色」（**空图事故**的事实陈述）当成「稳定锚点声称」去改 ⇒ 把**正确记录**改坏 ——
  本轮正是靠这一步避免了误改 `qa35b_recheck.sh:39` / `unity_batch.sh:127`。
- **数量类声称（N 条 / N 张 / N 处）必须能被一条命令核对，且与实现同批更新**。
  本批同类共 **4 处**：工具头注 `6→7`、`spec §11.6` `6→7`、`台账` `6→7`、以及「四张 / 84 条」（后者见 §11.6 对账）。
  ⇒ 这不是新规矩，是把已有的「**数字可复现 + 注来源**」（§9.6）落到「**条目数**」这一类上。
- **引用提交信息前必须 `git log -1 --format=%B <hash>` 逐字回读**（本批实测教训，与铁律 2 同源）：
  我曾把一条**写在 `spec`/`台账` 里的句子**当成「提交信息里写的」报给 team-lead 并要求评估改历史 ——
  实际 `ea9c39f` 全文只出现一处"锚点"（意为"锚到提交"），**没有** sha / "完全相同" / "稳定"。

- **「同批刷新」会作废同批里**先**写下的数字 ⇒ 顺序必须是「**先刷新证据 → 再写引用证据数字的文档**」**，

## 11.8 第 11 项：`PhysicsParams.cs` **行尾归一化（CRLF → LF）—— 无语义变化**
> ⚠ **本项与"内核改动"必须显式区分**：批次 B **本来不碰内核** ⇒ 这是本批**内核目录下唯一的改动**，
> 而它的性质是 **hygiene（只改行尾）**，**不是**行为/算法改动。

**由来**：`PhysicsParams.cs` 是**内核 8 个文件里唯一的 CRLF 文件**（**94 个 CRLF、0 个 LF**）；其余 7 个都是 LF（本轮逐一复核：`PoolSimulator` / `PoolMath` / `BallState` / `PhysicsTuning` / `ShotPrediction` / `Core/PoolGeometry` / `Core/PoolConstants` 的 CRLF 计数**全为 0**）。
**为什么是问题**：`.gitattributes` 的 `* text=auto eol=lf` + `*.cs text` ⇒ 仓库 blob 是 **LF**，而工作区字节是 **CRLF** ⇒ ① 新 clone 检出为 LF（同一修订在两台机器上"看起来不一样"）；② 任何按 CRLF 保存它的编辑器会话都会制造**伪 diff**（噪声）—— 与本工程"工作区必须干净"的冻结锚点纪律直接冲突。

**实测取证**：
| 项 | 值 |
| --- | --- |
| BEFORE | bytes **6,107**，CRLF **94**，裸 LF **0** |
| AFTER | bytes **6,013**，CRLF **0**，LF **94** |
| 只改行尾？ | ✅ 内容按 LF 归一后**逐字节相同**（`raw.replace(b"\r\n", b"\n") == raw2`） |
| BOM | 该文件**本就无 BOM**；本项只替换 `\r\n` ⇒ 不会增删 BOM |
| `git diff --numstat` | **空** —— 因为 git 读时即按 `.gitattributes` 归一 ⇒ 工作区现在**与 blob 一致**（**伪 diff 消失**，正是本项要的效果） |
| `git diff --ignore-cr-at-eol --numstat` / `-w` | **空** ⇒ **无实质差异**（= 只改行尾） |

**⚠ 结论（决定"提交里有没有这一项"）—— 本项修的是**工作区**，不是仓库**：
**决定性证据**：`git rev-parse :PhysicsParams.cs` == `git hash-object --path=PhysicsParams.cs PhysicsParams.cs`
== **`73716461ca1dff97a76646140dfa5b93b3e51538`** ⇒ **工作区经 clean 过滤后的 blob 与索引 blob 逐字节一致**；
`git ls-files --eol` 亦报 `i/lf  w/lf  attr/text eol=lf`（与 `PoolSimulator.cs` 同形态）。
⇒ **该文件在提交里不产生任何变更**（它把"工作区字节"对齐到了"仓库 blob"）——
**别在提交里找它**：它的价值是"**以后任何按 CRLF 保存它的编辑器会话不再制造伪 diff**"。
（另注：`git status` 可能仍列 ` M` —— 那是**陈旧 stat-cache** 的表现；**以 `ls-files --eol` 与 blob 相等为准**。）

**⚠ 与 `eq`（CoreCLR 逐位）基线的关系（必须写清，防后人误判）**：
**`eq` 基线的哈希是"物理产物的哈希"，不是"文件字节的哈希"** ⇒ **行尾归一化不动它**。
⇒ **不得**因为"内核目录下的文件 blob 变了"就认为"等价性结论作废" —— 那是**两个不同的量**（见 §11.9）。

## 11.9 【工具链】**两个 sha1 口径**（原始字节 / LF 归一化 blob）—— 与 §9.6 的 `3.3e-4` 是同一类坑
quality-lead 自查发现：他给的内核清单里 `PhysicsParams.cs = 03c537e1…`，而 git 里是 `73716461…`。
**差异来源 = sha1 的**口径**不同**：**工作区原始字节**（含 CRLF）vs **LF 归一化后的 blob**。
- 他复算 8 个文件：**7 个与 git 完全一致**，**只有这个 CRLF 文件两边不等**；
- 而且该文件**在两个提交里都没变**（内核 diff 仅 `PoolSimulator.cs`）⇒ **对 `eq` 结论零影响**。
⇒ **规矩（并入 §9.6）**：引用文件的 sha1 时**必须写明口径**（"工作区原始字节" 还是 "git blob（已按 `.gitattributes` 归一）"）；
**两个数不等 ≠ 文件被改**。这与 `3.3e-4 m` / `0.000337 mm` 那次是**同一类坑**：
**两个数看着不一样，其实不是同一个量。**

### 11.9b 第三个「两个口径」：`stat` 口径 vs **内容**口径（与前两类并列）
`git status` 可能因**陈旧 stat-cache** 报 ` M`，而 `git diff` **为空**。
⇒ **判定「是否改动」以 `git diff` / `git ls-files --eol` 为准，不以 `git status` 的字样为准。**
**三条同源**：① **工作区原始字节** vs **LF 归一化 blob**（sha1 口径）；② **像素内容** vs **计数口径**（`getdata` 那次）；
③ **stat** vs **内容**（`PhysicsParams.cs` 本次）。⇒ **同一个东西被两种口径描述，看起来不一样，其实不是同一个量。**

**⚠ 陷阱提示（照办）**：`PhysicsParams.cs` 在 `git status` 里**长期显示 ` M` 属预期**；
**不要为了让 `git status` 干净而对它做任何「还原」动作**（`git checkout --`）——
既有习惯「跑完批处理用 `git checkout -- <噪声文件>` 还原」对该文件**是安全的**
（`.gitattributes` 的 `eol=lf` 会在检出时写 **LF** ⇒ 不会把 CRLF 弄回来），**但前提是那条 attribute 在**：
**若将来有人改 `.gitattributes`，本项（行尾归一化）会失效。**

**⚠ 退出码两套语义不得互相套用（复核 D13）**：**冒烟** = `0` 达标 / `1` 未达标 / `2` 写盘失败 / **`3` 环境不洁**；
**`qa_render_evidence_check.py`** = `0` 通过 / `1` 证据退化 / **`2` 缺 Pillow（环境）**。两者**数字含义不同**，禁止互套。

### 12.2.6 本批立的流程规矩（逐条编号；标题不写条数 —— 条数会变，标题里的数字必过期）
1. **「约定」不是「机制」**：本轮撞了两次"双方都以为对方停手"。有效的是**可判定量** —— `mtime > 60 s` / `grep` 命中 / **离线编译门 0 error**，三样当**起跑前的固定前置步骤**，**约定只当补充**。⇒ 推论：**下位收到与已核实事实冲突的指令时，先拿可判定量核一遍再执行**（本轮 `(x = 0, y = 0.58)` 那条就是这么被**前提断言**挡下的 —— 它把「坐标选错」从**静默恒真**变成了一次**显式失败**）。
2. **注入不得跨窗口驻留**：注入态 = **已知错误的代码**，比「编不过」更危险（不会报错、结论静默失真）⇒ 备份 / 注入 / 跑 / 还原必须是**同一条原子序列**，注入态在树里存在的时间 = **一次 `tests` 的时长**。
3. **同一 `[Test]` 内的首条失败会掩盖后续** ⇒ 一条「**恒红**」会伪装成「后续都过了」（本批 `T138①` 就掩盖了 `T138④`、导致 `INJ3` 首轮没被考到）。⇒ **两层对策**：① 新判据**必须先在绿基线上跑过一次**（别让恒红/恒绿藏进新写的用例里）；② 同一用例承载**多个独立不变**时用「**收集全部失败**」范式，别用裸 `Assert` 串。**与「恒真守卫」是同一枚硬币的两面**（恒绿 = 没守住；恒红 = 守过头且掩盖别的）。
5. **注入序列必须逐条独立命令执行** —— **不得放进可能被超时 / `SIGTERM` 打断的单条批量命令**。实测（复核方本轮）：三组注入放进一条批量命令 ⇒ 被前台超时 `SIGTERM` ⇒ ① `F1` 的**还原步未执行**（树里一度残留注入态，随后已补还原、`marker` = 0）② 留下 `Temp/UnityLockfile`（`mtime 19:36:14`，已按两条件门清除）。⇒ 与「**编译失败退出不清锁**」并列：**非正常退出都不清锁**；且**注入态驻留 = 一条命令 + 一次跑批**（缩短驻留窗口的另一种形态）。

   **注入期互斥（与上一条合并：前者=缩短窗口、后者=互斥，缺一不可）**
   「注入态驻留 = **一次 `tests` 的时长**」**只在单写手下成立**；注入态存在期间，**工作区对任何其他读者都不可信**。
   实测（本批）：`F1` 注入态存活 ≈`19:36:20` → ≈`19:37+`，期间**另一写手读过 `git status`（看到 21 项）并据此还原了 3 个噪声文件** —— 本例**无实际影响**（只碰台账 + 噪声文件、未碰源码；注入只改本就在冻结集内的 `PhysicsTestDrive.cs` ⇒ 其计数解读恰好自洽），**但这是侥幸**。

## 12.4 本批（用户第三轮实测截图）：瞄准线的**三个真缺陷**（A 残留 / B 两圈 / C 指袋时圆跑到台面正中）

用户三张截图逐条对应一个**真缺陷**（不是观感差异）：①「怎么发射完还留线」②「怎么有两个圈」③「白线指向球袋时…圆圈分离出来了」。

### 12.4.1 缺陷 A：出杆后白线**残留**
- **根因**：`LateUpdate` 的清空分支只调 `SyncRenderers(empty)`（清**虚线池**）与 `SyncContactMarkers(default)`（清标记），
  **没有碰 `_pathLine`** —— 而白线载体在上一轮已由"按弧长铺的虚线池"换成"整条折线 = **一个** `LineRenderer`"。
- **修法（单点）**：抽 `HideAllAimVisuals()` 为**唯一实现点**，**显式枚举**清 6 项：虚线池（已退役、仍一并清）／`_pathLine`／
  `_ghostCircle`／`_cushionCircle`／`_targetLine`／`_cueDeflectLine`；`LateUpdate` 清空分支**只调它**。
- ⚠ **迁移检查清单（本处最值钱的一条）**：**换渲染载体时必须同时更新"所有"引用该载体的路径** —— **绘制 / 清空 / 显隐门 / 池回收**，
  并**加一条"清空后无残留"的判据**。本缺陷漏的正是"**清空**"那一列。

### 12.4.2 缺陷 B：**两个圈**（且库边首碰时黄/蓝线也在画）
- **根因**：幽灵球圆用 `prediction.HasFirstContact`（= **球-球**接触，**可能在碰库之后**才发生），库边圆用 `HasCushionFirstContact`
  （= **首个**接触是库边）⇒ 在"先碰库、再碰球"的杆里**两者同时为真**。代码里那句「**两圆互斥，不会叠**」是**假陈述**
  —— 它默认了"`HasFirstContact` == 首个接触"，该前提不成立。
  **同源**：黄线（目标出射）与蓝线（白球偏转）也按 `HasFirstContact` 画 ⇒ 库边首碰时也在画，而那两段是**反弹之后**才发生的事 ⇒ **语义错误、误导**。
- **修法（单一实现点的纯函数）**：`MarkersFor(ContactKind firstContactKind, bool hasFirstContactEvent)` 决定该显示哪组标记；
  视图侧四个标记的可见性**全部由 `markers.*` 门控**（不再直接读 `prediction`）。

### 12.4.3 缺陷 C：白线指向**球袋**时圆圈画到**台面正中**
- **根因（两半叠加）**：① `MarkersFor` 的 `else` 分支把**一切"不是 Cushion"** 的类别当成"球首碰" ⇒ **`ContactKind.Pocket`（越袋喉）也落进去**
  ⇒ 去画幽灵球圆；② 而"无球-球接触"时 `Prediction.GhostBall` **从未被赋值**（提前返回分支里没有它）= `default` = **(0,0)** = **球桌中心**
  ⇒ 圆画在台面正中、与停在袋口的白线末**分离**。
- **修法（三件）**：① `MarkersFor` 改**穷举 `switch`**（`Cushion`／`BallBall`／**`Pocket`**／`default` 全 false）⇒ **删掉兜底语义**；
  ② 新增**显式** `HasBallBallFirstContact`（**不要用「类别 != Cushion」反推**）；
  ③ **根治：删掉 `CushionContactPosition`** —— 视图/判据一律只读**一对** `FirstContactKind` + `FirstContactPosition`（对所有类别都填）
  ⇒ "**读了没被赋值的字段 ⇒ 画到 (0,0)**"这**一整类** bug 从此不可能发生。
