## 1. 任务①：`Main.unity` 成为正式游戏入口

### 1.1 现状（改前）与病根

- `Main.unity` 改前是**空壳**（1 个 `MeshRenderer` + 1 个 `Camera` + 1 个 `Light`、**0 个 MonoBehaviour**）⇒
  用它出包 = **黑屏死包**。
- 出包入口因此一度被迫改用灰盒场景（`PerformanceSetup` / `BuildWindows` 指向 `PhysicsGreybox.unity`），
  代价是**与 `SCN-02`（Day1）与 `D4-BLD-01`（Day4）互斥** —— 那两条断言**提交态 build list 恰好是
  `[Main.unity]`**，而 `BilliardsProjectSetup.Apply` 每次又把它写回 `Main.unity` ⇒ "谁后跑谁生效"。

### 1.2 改法（as-built）

**唯一实现点**：`GreyboxSceneSetup` 新增

| 成员 | 作用 |
| --- | --- |
| `MainScenePath` | `Assets/_Project/Scenes/Main.unity` |
| `MainGameplayRootName` = `GameplayLayer` | 玩法层根对象名，**同时是幂等标记** |
| `AttachMainGameplayLayer(Scene)` | **把玩法层叠加到既有 Main**（复用桌/地面/相机/光；见下） |
| `ApplyMainScene()` | **幂等**：`MainHasGameplayLayer()` 为真 ⇒ **早退不写盘** |
| `RebuildMainScene()` | 强制：打开 Main → 回收旧玩法层 → 重新叠加 → 保存 |
| `BuildGameplayHosts(...)` | **玩法层宿主的唯一构建点**（灰盒与 Main **共用**，铁律 16） |
| `BuildFromCommandLine/RebuildMainFromCommandLine` 等 | `-executeMethod` 入口 |

`AttachMainGameplayLayer` 的四步：
1. 复用既有 `PlayfieldRoot` 与名为 `Main Camera` 的相机；
2. 给相机**缺失才补** `AudioListener` / `CameraViewportFitter`（**绝不新增第二台相机 / 第二个监听器**）；
3. 回收并重建球可视物（白球 + `RackBall_1..15`），挂**既有** `PlayfieldRoot` 下；
4. 在 `GameplayLayer` 根下建全部玩法宿主（调试叠加层**关**）。

同时把原 `BuildScene()`（灰盒）**重构成调用同一个 `BuildGameplayHosts`**（相机在建玩法层之前建好），
并把 `MaterialVisualSetup.BuildScene()` 的末尾接上 `AttachMainGameplayLayer(scene)` ——
**保证两条写入路径都产出完整 Main**（否则"Build Materials, Scene & Prefabs"会把玩法层洗掉）。

**出包口径统一**：`PerformanceSetup.BuildScenePath`（原 `GreyboxScenePath`）与 `BuildWindows` 均指向
`Main.unity`；`T120 ③` 由"断言灰盒场景非空壳"改回**断言 `Main.unity` 非空壳**（含驱动器 / HUD / 瞄准辅助）。
⇒ 互斥的根因（"Main 是空壳"）消除，`SCN-02` / `D4-BLD-01` **变成真正正确**。

## 3. 任务③：拖动瞄准的卡顿

### 3.1 三处成本（改前）

1. `AimAssistController.Fingerprint`：每帧对 17 球 × 4 个 float 走 `ToString("R") + StringBuilder`；
2. `RefreshPrediction`：拖动时指纹每帧都变 ⇒ **每帧**跑一次 `ShotPredictor.Predict`（最多 **240 步**）；
3. `AimAssistView`：每帧 `new List` + 每段各建一个列表；且**逐路径取样点**铺虚线
   （每段至少 1 段 ⇒ ~240 个 `LineRenderer`）。

### 3.2 改法（as-built）

| 位置 | 改动 |
| --- | --- |
| `AimAssistController` | 指纹改 **64 位 FNV‑1a 数值哈希**（零分配、零字符串）；新增 **`ShouldRecompute` 纯函数**（前沿节流 + **尾沿强制**）；新增 `minRecomputeIntervalSeconds`（默认 `1/30` s）；用 **`ShotPredictionWorkspace`** 复用探测内核与缓冲 |
| `ShotPredictor` | 新增**带工作区**的重载（复用探测内核 + 快照 + 路径缓冲）；4 参旧重载**输出逐位不变**（内部新建一次性工作区） |
| `ShotPredictionWorkspace`（新） | 持有可复用探测内核 + 快照/路径缓冲；缓存键 = (桌, 参数, 三个标量)，不符即重建；复用路径**显式补一次 `ResetDiagnostics()`**（`LoadBalls` 不清每杆计数） |
| `AimAssistView` | 虚线段缓冲复用；新增 **`AppendPolylineDashSegments`**（**按弧长**铺虚线 ⇒ 段数只由路径总长决定）；**只在预测重算过（版本变化）时重绘** |

**硬约束（尾沿）**：`ShouldRecompute` 在"本帧指纹 == 上一帧指纹"（= 输入已停止变化）时**无条件返回 true**
⇒ **停止拖动后的下一帧必定是最新预测**，瞄准线不会停在旧值。

### 3.3 可测证据（新增冒烟模式）

`SmokeProbe` / `SmokeProbeRunner` 新增 **`-billiards-smoke-aim`**（无值标志）：采样期间**每帧连续改变瞄准角**
（`AimSweepDegrees(frame) = (frame × 4.5°) mod 360`）⇒ 逼出"预测重算"这条最坏路径。
运行时挂钩走 **Core 定义、Physics 实现**的接口 `ISmokeAimSweepTarget`（**不产生反向依赖**）。

`unity_batch.sh` 新增 `smoke-aim` 步骤。判定口径：
- **静置**：沿用原**严格闸门**（`MeetsTarget`：均值 ≤ 16.67 ms、掉帧 ≤ 2%）——**未改**；
- **拖动**：新增 **`MeetsDragTarget` 宽松闸门**（均值 ≤ **50 ms**、掉帧 ≤ **40%**）。

### 3.4 ⚠ 实测结论（如实，**这是本单最重要的发现**）

| 冒烟 | 均值 | p95 | 最大 | fps | 掉帧 | renderer | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 静置 600 帧 | 6.94 ms | 6.95 ms | 6.95 ms | **144** | 0 / 600 | **27** | ✅ 严格闸门通过 |
| **连续拖动瞄准 600 帧** | **24.9 ms** | **76.3 ms** | 83.4 ms | **40** | 162 / 600（27%） | **34** | ✅ 宽松闸门通过 |

- **旧盲带被关闭**：改前冒烟只测静置 ⇒ 拖动峰值**从未被测过**。现在它是**可判定**的。
- **残差归因（实测+推算）**：拖动帧的额外成本**主要来自预测重算本身**，不是渲染 ——
  证据：`AppendPolylineDashSegments` 把 `rendererCount` 从 **260 降到 34**（~7.6×），
  但均值只从 26.1 → 24.9 ms（~5%）⇒ 瓶颈不在渲染器。
  单次重算 ≈ 最多 **240 步** × 内核单步 ~0.37 ms（Day16 实测静止单步）≈ **数十毫秒**，
  与观测到的 p95 ~76 ms 同量级 ⇒ **内核固有成本**。
- ⇒ **拖动路径无法同时满足"60 fps 且掉帧 ≤ 2%"**（一次同步重算就吃掉数帧）—— 该"闸门"会**恒红**、
  等于没有判据。故拖动路径用**宽松闸门**（只拦量级失控），**不声称 60 fps**。

## 5. 盲带（如实）

1. **拖动帧率**：拖动瞄准 40 fps（均值 24.9 ms）**低于 60 fps**；达到 60 fps 需要**更廉价的预测模型**
   或**较短的拖动期步数上限**（后者是**可见**权衡：拖动中瞄准线变短、松手恢复全长）——**未实施，待裁定**。
2. **拖动期"卡顿"的主观观感**不由判据判定（`R3-4`）；本单只给出**帧时数字**。
3. **虚线段数变化**：按弧长铺虚线会改变虚线的**断点位置与段数**（观感略更"实"）；无自动判据覆盖
   "观感是否变差"（`T80` 只判"间隙 > 0 且 ≥ 屏幕可辨下限 + 段数闭式"，且那条测的是**单段**函数，未变）。
4. **`OnGUI` 实际绘制**不在 EditMode 可判范围（无渲染派发）⇒ `T129 ③/④` 只保证**结构**。
5. **无改前拖动基线**：拖动冒烟是**本单新增**的，因此**不存在**"改前 vs 改后"的同类数字
   （改前从未测过——这正是被关闭的盲带）；可对比的是 `rendererCount` 260 → 34（同一路径、两版之间）。
6. `MaterialVisualValidator` 的 **day3 渲染证据图**在跑验收器时会被覆写（改了 Main 的内容）⇒
   本单按纪律 `git checkout -- Docs/Reports/` 还原，**不把 day3 入库证据更新为本单版本**（待裁定）。

## 9.3 等价性论证（**与浮点精度无关**，故跨运行时成立）
**精确事实（ℝ）**：球心到线段距离 ≤ r ⇒ 取最近点 q（q 必落在段端点 AABB 内）⇒
`|p.x − q.x| ≤ r` 且 `|p.y − q.y| ≤ r` ⇒ `p.x ∈ [minX − r, maxX + r]`、`p.y ∈ [minY − r, maxY + r]`。
TOI 侧**同一推理**：接触 ⇒ 扫出 AABB 与 段AABB⊕r 相交。
⇒ 预筛盒 = **段AABB ⊕ (r + ε)** ⇒ 该蕴含**严格保留** ⇒ **被跳过的对必然不重叠 / 必然不接触**。
⇒ **ε 只吸收"构造预筛盒那几步加减"的舍入**（尺寸 ~1 m 时约 1e-7），取 **1e-6 > 2× 该界**
⇒ 即便按浮点最坏情况取值也不会误跳 ⇒ **结论跨 Mono / CoreCLR 同成立**。**全工程无"严格比较不留余量"写法。**

## 10.6 教训（写给后来者）
- **"绿而空"**：判据亮绿**不等于**证据有信息；**任何"只查存在/只查落盘"的判据都有这个洞**。
- **两个空洞判据会互相掩护**（一个只数文件、一个永不失败）⇒ 空洞被**两个**绿灯共同掩盖，且看起来"很正常"。
- **正解 = 事前拦截 + 两层同判**：判据内断言"非退化 / 有差异"，工具外每次刷新**自动**再查，且工具**自带自证**。
- **别让"存在"冒充"有内容"**：**文件大小下限 + `distinctColors > 1` + A/B 差异**，三者合起来才够。
- **先看时间戳 / 指纹，再下结论**：判定"是否修好"**必须看产物的 `mtime` + `sha`**，**不能凭"最近一次刷新"这个说法**。
  本例：**同一现象被两次观测、而时间点不同** —— `11:21:00` 的产物（`-nographics` 下刷新所得）是**空图**（19,069 B / sha `b5c699d043f0` / `distinctColors = 1`）；而**修复后**的 `11:25:32/33` 与最终 `11:30:38` 是**真图**（1.2 MB / 11,612 色 / sha `ff216b885e09` …）。⇒ 那句"仍是空图"来自**前者**，**两次观测都没说错**，只是**观测时刻不同 + 消息在途**。
  ⇒ 这是本工程"**先看时间戳再下结论**"的**第 3 次**教训（前两次：把上一轮的结果 XML 当本轮结论读；跑批工具补上 mtime 打印）。
  附：修复后**两次独立渲染（11:25 / 11:30）四张 sha 完全相同** ⇒ 这些 sha 可作**稳定锚点**（将来若变 = 真实变化）。
