## 一、结论先行

**三个核心判断，先说明，因为它们决定了整份排期：**

### 1. 台球物理必须自研 2D 定长步进模拟器，不能用 Unity PhysX

这是本项目最关键的一次技术选型。理由如下：

| 方案 | 评估 |
| --- | --- |
| PhysX 3D 刚体球（SphereCollider + Rigidbody） | **不推荐。** 球半径仅 0.028575 m，出杆初速需 2–8 m/s，连续接触（球堆开球）时 PhysX 的离散碰撞检测易穿透；滚阻/旋转摩擦无法精确控制；库边为网格碰撞体时接触法向抖动，导致"诡弹"。台球对确定性要求极高，PhysX 无法保证同初值同结果 |
| 第三方确定性物理库 | 需引入外部依赖并自行验证，收益低于自研成本 |
| **自研 2D 定长步进（本项目采用）** | **推荐。** 美术包已提供**完整的、已标定的 2D 碰撞数据**：`08_Gameplay_Markers/table-metadata-reference.json` 含 82 段库边线段（含袋角弧段）、6 袋的袋口/袋喉/内沿坐标与 `captureRadius = 0.03074`、`clothHeight = 0`、`ballRadius = 0.028575`、内库 2.54 × 1.270108866 m。原型 `pool-engine.js`（739 行，含 561 行物理单测）已验证该模型可行。自研后：完全确定性 → 瞄准预测线、AI 推演、回放全部免费获得 |

实现形态：物理在**规范米制的二维平面**（长轴 × 短轴）上运算，渲染层按 `(x, 0, y)` 映射到三维。这与原型的 `physics2d_to_runtime3d` 约定一致。

### 2. 排期必须"物理先行、美术后接"

策划备注写得很明确：**"物理不真就'台球乱弹'"**。因此 Day 1–7 全部投入工程基建 + 物理内核，美术仅做最低限度的桌面材质，**不导入任何布景**。Day 7 设一个强制 Go/No-Go 闸门：灰盒物理打不出"不像乱弹"的手感，就地停下调参，不进入 Phase 3。把最贵的风险放在最前面。

### 3. 原型源码只能当算法与参数参考，不能当代码复用

`Playable_Prototype_Reference` 是 three.js + planck（JS），Unity 侧是**从零重写**。可复用的只有：碰撞数据、参数直觉、UI 流程与状态定义（`data-state`）、VFX 的表现意图。切勿按"有原型所以快"来估工期。

## 二、35-A 的范围边界

### 要做（In Scope）

- 1 张标准球桌 + 16 球 + 1 球杆
- 完整的击球物理闭环：瞄准 → 力度 → 出杆 → 碰撞 → 停止
- 82 段库边 + 6 袋的真实碰撞与捕获
- 瞄准辅助（瞄准线 / 幽灵球 / 目标球预测线）
- 击球与进球的音画反馈
- 练习模式最小 UI（HUD + 练习结算）
- 手感相关数据埋点

### 明确不做（Out of Scope，属 35-B）

- **AI 对战**（含失误率设计）
- **8 球完整规则**：分球组（solid/stripe 归属）、指定袋（call pocket）、犯规判定（先碰错球/未碰库）、自由球（ball in hand）、三局两胜
- 联机、账号、排行榜
- 完整 8 组 UI 闭环（加载/首页/赛前/设置/暂停/确认）
- 房间布景（长椅、落地灯、挂画、植物、球杆架等 13 类布景模型）

> 最小例外：**白球落袋后重置到开球点**属于物理闭环必需，要做；但"犯规判定与自由球摆位"不做。
