## 1. 构建入口实际做了什么（读码结论，非推测）

`Assets/_Project/Scripts/Editor/ProjectSetup/BuildWindows.cs`：

1. 先跑 `PerformanceSetup.Apply()`（幂等）：URP `PC_RPAsset` 阴影距离 → **6 m**、级联 **1**、主光阴影图 **2048²**，并把 `EditorBuildSettings.scenes` 设成**恰含并启用 `Main.unity`**，随后**回读校验**；失败 ⇒ 退 2、不出包。
2. 断言构建场景列表；不符 ⇒ 拒绝出包（防"打出没有逻辑的空壳包/黑屏死包"）。
3. `BuildPipeline.BuildPlayer` 出包到 `Build/Windows/Idea35PoolRoom.exe`，`BuildOptions.None`。
4. 自检 `exe` + `Idea35PoolRoom_Data/` + `_Data/Managed/` + `UnityPlayer.dll` 齐备，落 `build-report.json`。
5. 退出码：0 = 出包且自检通过；1 = 构建失败；2 = 配置/场景断言失败；3 = 产物自检失败。

## 3. 为什么 exe 的 mtime 没变（不是假构建）

验收口径原为"exe mtime 必须晚于构建开始时刻"。**该口径在本工程上不成立**，原因已用哈希坐实：

```
fce862f1e3103b673f13db54b9a8d278eeed3cf3704425db30b34ffed2c704cb  Build/Windows/Idea35PoolRoom.exe
fce862f1e3103b673f13db54b9a8d278eeed3cf3704425db30b34ffed2c704cb  <Unity>/PlaybackEngines/WindowsStandaloneSupport/Variations/win64_player_nondevelopment_mono/WindowsPlayer.exe
260b5fdcaefdc2c9b90b3c0cc4042284f9324b5eba0783e965ea55e4322d091a  Build/Windows/UnityPlayer.dll
260b5fdcaefdc2c9b90b3c0cc4042284f9324b5eba0783e965ea55e4322d091a  <同上目录>/UnityPlayer.dll
```

- `Idea35PoolRoom.exe` **就是 Unity 的通用启动器模板 `WindowsPlayer.exe`，逐字节相同**；`UnityPlayer.dll` 同理。
  这两个是**与游戏内容无关的平台二进制**（游戏代码在 `_Data/Managed/Billiards.Runtime.dll` + `_Data/*` 里）。
- Unity 构建时对内容未变的文件**跳过重写**（保留原 mtime），所以只要用的是同一个编辑器版本，这两颗文件的 mtime 就永远停在第一次构建的时刻。
- 佐证：`10-16 18:37` 那次构建同样报 `exeBytes = 672256`、exe mtime 同样停在 `10-15 23:49`——同一现象，不是本轮偶发。

**⇒ 建议把发布门控的"新包"判据改为：`Billiards.Runtime.dll` 的 mtime + `_Data/level0`、`globalgamemanagers` 的 mtime + `build-report.json` 的 mtime 全部晚于构建开始时刻**（本轮三条全过）。exe/UnityPlayer.dll 的 mtime 不适合当判据。
