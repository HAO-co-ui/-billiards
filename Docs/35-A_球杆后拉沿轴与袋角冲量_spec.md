## 2. 问题 A：蓄力时球杆穿库

### 2.1 实测定位（从用户截图量出来，不是猜）

用像素连通域把截图 1 里的**球杆像素**（木棕/橙）分离出来，得到 3 个连通块：

| 块 | 位置（原图 px） | 说明 |
| --- | --- | --- |
| 杆身段 1 | x∈[356,405]，y∈[166,196] | 台呢上可见（靠杆尖一侧） |
| 杆身段 2 | x∈[446,552]，y∈[86,144] | 台呢/库边上方可见 |
| 杆身段 3 | x∈[580,611]，y∈[50,70] | 台面之外可见 |

三块**共线**（拟合斜率 −0.565，逐块端点误差 < 2 px）⇒ 同一根杆，中间两段被 **①绿呢库边（x≈407–446）**
与 **②木库外缘/台外区域（x≈554–580）** 遮挡 ⇒ **杆身在库边两侧都不可见 = 整根穿过库边**。

标定：白球可视直径 = `2 × 0.028575 × 1.2 = 0.06858 m`，实测 ≈ 23 px ⇒ 1 px ≈ 0.0030 m。
杆尖（可见端 x=356）到球心（x=214）的距离 = 163 px ≈ **0.47 m** ≈ `TipGap + MaxPullback = 0.46 m`
⇒ **用户处于拉满力度**（这一点很关键，见 2.2）。

### 2.2 根因

`StickElevationDegreesFor` 的反解**以"杆身落在过球心那条直线"为前提**：
需求 = 「杆身跨过台面外缘处，其下表面高于全桌最高点」，`sinθ ≥ (OuterBoundsMax.y + StickRadius − BallRadius) / d`
（`d` = 球心沿杆身方向到台面外缘的水平距离）。而旧实现把后拉量沿**水平方向**加：

```csharp
// 旧：杆尖 = 白球中心 − 瞄准方向 ×（静止间隙 + 后拉量）   ← 平移，不带高度
```

⇒ 杆身被整体向库边**平移** `(TipGap + pullback)`，却**一点额外高度都不带** ⇒ 杆身在跨库处的实际高度
比反解预测低 `(TipGap + pullback)·tanθ`。

用户截图姿态的量化：`d ≈ 0.62 m`（由 222 px 标定）⇒ 需求角 `asin(0.040425/0.62) = 3.74°`
⇒ 被 `MinStickElevationDegrees = 4°` 兜住 ⇒ θ = 4°。此时**跨库处**杆身抬升只有
`(0.62 − 0.46)·tan4° = 0.0112 m`，而需求是 `0.0324 m` ⇒ **只有三分之一** ⇒ 必然整根穿库。

**注意**：上一轮已经修过一次"固定 4° 不够"（改成按球位反解），但反解的前提被**水平后拉**破坏了 ——
判据 `T104 (e) ③` 当时算的正是"过球心那条线"的高度，**与实现画的不是同一条线** ⇒ 判据看着过、实机照样穿。

### 2.3 修法

**后拉沿抬升后的杆身轴线**（真实球杆就是这么后拉的）：

```csharp
// 新：杆尖 = 白球中心 + StickDirection(瞄准方向, 抬升角) ×（静止间隙 + 后拉量）
public static Vector3 StickTipPosition(Vector3 cueBall, Vector3 aimDir, float pullback,
                                       float elevationDegrees = 0f)
```

则杆身**恒在过球心的直线上**，杆上位点高度 `h(ξ) = 球心高 + ξ·tanθ`（`ξ` = 到球心的水平距离）
**与后拉量无关** ⇒ §2.2 的反解对**任意后拉量**成立（含"杆尖已被拉到库外"的情形：那时
`h = 球心高 + ξ_t·tanθ ≥ 需求`，因为 `ξ_t > d`）。

- `elevationDegrees = 0`（默认实参）⇒ 退化为历史"水平后拉"，`T88` 的 1:1 逐位不变；
- 生产路径（`SyncStick`）传 `elevation`；顺序改为**先算角、再定位杆尖、最后定向**；
- 杆长、观感、蓄力跟手**均不变**（`MaxPullback` 仍是 0.45 m，沿轴后拉的水平分量 = `P·cosθ ≈ P`）。

## 3. 问题 B：球撞袋角"没有一点弹力、吸在两边"

### 3.1 离线复现（不依赖 Unity）

工具：`Docs/Tools/jaw_impulse_repro.py`（把内核的 `SolveToi / EarliestSegmentToi / ResolveContactGroup /
ResolveSegmentContact / ResolveDeepOverlaps` 按 C# 逐条转写，几何取权威
`Docs/Reference/table-metadata-reference.json` 的 82 段与 6 袋）。运行：`python Docs/Tools/jaw_impulse_repro.py`。

**机制**：袋角侧壁是**一串共享端点的短段**（4–25 mm，球半径 28.6 mm）。球撞在两段的**公共端点**上时，
`SolveToi` 会对两段各调用**同一个端点圆**的 `RayCircleToi` ⇒ **同一个接触事件被收成两条同刻条目**：

| 条目 | 法向速度 `v_n` | 修复前的动作 | 结果 |
| --- | --- | --- | --- |
| 第 1 条（袋角段） | `−0.084`（正在接近） | 正常反射 | 球朝外 `+e·0.084` |
| 第 2 条（直库段） | **`+0.142`（已在分离）** | **仍被无条件反射** | 把球**翻回库内** `−0.114` |

修复前 `ResolveSegmentContact` **没有接近判据**（而球-球路径 `ResolveBallBallContact` **有**：
`if (v_n >= 0f) { ...return; }`）⇒ 同一接触被解算两次、第二次把第一次正回来，球带着"朝库内"的速度
进入深层重叠 ⇒ 下一子步被位置修正推回、再被翻回，每轮法向 ×`e²`、切向还各吃一次摩擦
⇒ **速度被逐步吃光 ⇒ 球停在袋角不动**。

### 3.2 实测（`Docs/Tools/jaw_impulse_repro.py` 输出）

统计「接触解算后**仍有相触库段正在被撞进去**」（`min v_n < 0`；随机 6000 姿态/区域）：

| 区域 | 修复前 | 修复后 |
| --- | --- | --- |
| 全台面随机 | 3.7% | **0.1%** |
| 中袋袋角区域 | **11.8%** | **0.1%** |
| 角袋 #0 袋角 | **11.9%** | **0.1%** |

⇒ 与用户"**只在袋角**感觉得到"的观察一致（袋角 12% vs 台面 3.7%）。

端到端（单球全步进，含袋口判定；两个代表姿态与判据 `T109` **同一对**）：

| 姿态 | 修复前 | 修复后 |
| --- | --- | --- |
| (a) TOI 路径：斜入 −y 中袋袋角（接触点 = 段 19/20 公共端点，侵入深度 28.6 mm） | 球**停在袋角** `(0.0975, −0.6081)`、`|v| = 0`；接触条目 48、深层重叠修正 162 | 以 `(−0.79, +2.25) m/s` **弹回台内**；接触条目 2、深层重叠 0 |
| (b) 深层重叠路径：球卡在袋角凹角（与 3 段重叠 ~16 mm） | `|v|` 逐帧塌陷 `0.155 → 0.023 → 0.0035 → 0.0005` ⇒ **死在原地** | 离开袋角（`|v| = 1.35`，随后被该袋正常捕获） |

姿态 (a) 的解析校核：入射 `v=(0.993,−2.813)`、接触法向 `n=(−0.331,0.944)` ⇒ `v_n = −2.984`
⇒ 出射法向分量应为 `e·|v_n| = 2.387` ⇒ 出射 `(−0.786,+2.256)`，与实测 `(−0.79,+2.25)` 吻合
⇒ 修复后是**标准弹性反射**。

### 3.3 修法

补上**与球-球路径同一条接近判据**（铁律 16：同一不变量单点、两路径口径一致）：

```csharp
float vn = Dot(v, n);
if (vn >= 0f) { return; }      // 已在分离 ⇒ 不施加冲量、不计接触事件
```

- 位置修正**不在此处**（深层重叠由 `ResolveDeepOverlaps` 先修位置）⇒ 跳过冲量**不影响**
  "球不得静默钻入库边"；
- 计数口径与球-球路径对齐：**只有真的施加了冲量**才算一次接触（`TotalContactCount` / 接触事件）。

## 6. 验证期暴露的三处**旧判据/旧场景口径问题**（本单必须连带宽处理）

这三处都**不是**"改判据求绿"，而是"旧检查量错了对象"。三处的共同判据：**先做因果对照**（把本单改动去掉 ⇒ 旧结果是否逐位复原），再决定重钉。

### 6.1 `T28b` / `T32b` 的擦角场景落在**捕获口径**之内（口径冲突，已裁）

- 场景：`start = tc − 0.12·tn + 0.045·td`、`v = 2·tn` 射向角袋，断言"**擦袋角不应被捕获**、不越喉平面"。
- 事实：角袋嘴半宽 ≈ 0.0727 m、球半径 0.0286 m ⇒ 「球能否从嘴口挤过去」的临界偏移 = **0.0441 m**。
  `ρ0 = 0.045` 只比临界值大 **0.9 mm**（擦切退化），而 `0.045 ≤ openingRadius = 0.0613`
  ⇒ 按裁定 A 的口径，球心一旦越过喉平面**就是入袋**。
- ⇒ 旧实现之所以"没入袋"，是因为球被袋角**钉住**（正是本单修掉的缺陷，且 `T32b` 的 doc 早已把
  "擦角球嵌入袋角反复解算、实测 `TotalContactCount ≈ 798`"**登记为已知行为**）。
- **处置**：把 `ρ0` 由 **0.045 → 0.060**（啮合由 0.9 mm 提到 16 mm，成为真正的"撞袋角"），
  断言一字不放宽 ⇒ 场景回到它声称的语义"**袋角必须把球封堵在台面上**"。
  三处胶水同步：`T28b`（`PoolSimulatorPocketCaptureTests`）、`T32b`（`PoolSimulatorTerminationAndBreakTests`）、
  `T72b` 内的同场景副本（`PoolSimulatorBallBallContactDiagnosticTests`）。

### 6.2 `T7` 的直库硬门**结构性依赖穿透**（已补判据）

- `T7` 用**扫掠弦**（两个采样点连线）判接触。对**平面段结构性不可见**：球心恒在平面外侧，而
  "到半平面的距离"是**凸函数** ⇒ 弦上最小距离 ≥ 两端点最小距离 ≥ `r`；除非接触恰落在采样边界
  ~1.4e-5 s 内，弦**永远够不到**平面段。
- 实测：直库段（6/20/33/47/61/74）在本单修复后命中 **0** 次 —— 而**同一批发射**在探针里
  `TotalContactCount` 明明记录了撞库、球也确实反弹（`seed=(0,0)→seg20 mid`：step 20 处
  `contacts` 由 0 变 1、速度由 `(+0.707,−0.707)` 变为 `(+0.707,+0.707)`）。
  ⇒ 旧实现里这 6 条**只能靠"球真的嵌进库段里"（球心进到 r 以内）被弦看见**，而"嵌进去"正是被修掉的缺陷。
- **处置**：新增**折返反射**判据（与内核计数无关）：速度方向折返 ⇒ 由 `v_out − v_in` 反解碰撞法向、
  归给"一个步长内可达且法向最一致"的段。两条**一起用**（弦覆盖角点类、反射覆盖平面类）。

## 7. 盲带与登记

1. **`T109` 的盲带**：只覆盖两个代表姿态；"同一接触点被两段各收一次"这一**结构性**现象仍在
   （接近判据只让它不再产生错误冲量）；**凹角里多约束互相顶的残余**（离线统计 ~0.1%）未消除
   ⇒ 登记 35-B 候选（需要迭代式求解器 / 流形去重）。
2. **抬升角上限带**：需求取全桌最高点（木库顶面 0.061 m），比袋口附近实际遮挡更保守；
   球心离库边外缘 < ~57 mm 时 45° 上限仍可能擦过库边顶部（需库边/木库**分段高度数据**，美术包未给）。
3. **`StickTipPosition` 的默认实参**：`elevationDegrees = 0` 保留历史语义（`T88` 用），
   生产路径必须显式传角 —— 由 `T104 (e) ⑤` 守住"杆尖在轴线上"这条结构性前提。
4. **接触计数语义变化**：段接触的 `TotalContactCount` / 接触事件现在**只在真的施加冲量时**递增
   （与球-球路径一致）⇒ 既有接触数基线按 §6.3 重钉。
5. **`T7` 的弦几何盲带**（§6.2）：平面段接触对"边界采样的弦"结构性不可见 —— 这不是本单引入的，
   是**一直存在**的测量盲带；本单用反射判据补上，但**弦判据本身仍不覆盖平面类**
   （若将来有人删掉反射判据，直库门会重新红 —— 这是刻意的，见 `T7` 的类注释）。
