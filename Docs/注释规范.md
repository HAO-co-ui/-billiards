# 注释规范

> **目的**：注释必须**自足且无时间性** —— 一个完全不了解本项目排期的人，只读代码与注释，
> 就能知道「这段代码做什么、为什么必须这么写」。
>
> **起因**：代码注释里混入了大量**排期与批次标签**（`Day 4 切片 C`、`D4-FIX-03`、`R1 冻结`…）。
> 这类标签对读者**零信息量**：它们只说明"这行是第几天写的"，不说明代码为什么是这样。
> 更糟的是它们**会过期** —— 排期表一变，"Day 4"就指向一个不再存在的语境。

---

## 1. 硬规则

### 1.1 禁止出现（开发日 / 批次 / 轮次 / 实验标签）

| 类别 | 例 |
| --- | --- |
| 开发日 | `Day 4`、`Day4`、`第 4 天`、`切片 A/B/C` |
| 任务号 | `D2-T02B`、`D2-T02A`、`D3-T02`、`D2-T04` |
| 批次号 | `D4-FIX-01`、`D4-C3`、`D4-GAP-02`、`D4-VERIFY-03`、`RENAME-01` |
| 轮次 | `R1 冻结`、`R2 独立确认`、`R3 增量确认`（**当作开发轮次用时**） |
| 实验标签 | `Run A/B/C/D/E`、`V-2`、`V-3`、`V-4`、`任务 #26` |

### 1.2 必须保留（**这些不是时间，是锚点**）

| 类别 | 例 | 理由 |
| --- | --- | --- |
| 标准 / 铁律编号 | `铁律 4`、`铁律 10`、`R1-3a`、`R2`、`R3-5`、`R5-3`、`R5-4` | 稳定规则编号，指向 `Docs/工程标准.md` / `Docs/项目纪律铁律.md` 的确定条目 |
| **检查项 ID** | `D4-PHY-01`、`D4-SCN-01`、`D4-SCN-02`、`D4-BAN-01`、`D4-BLD-01`、`SCN-0x`、`LYR-0x`、`RUN-01` | **它们是已入库证据 JSON 的键**（逐字出现在 `Docs/Reports/*.json`）。改名 = 作废全部已入库证据 |
| 提交哈希 | `4b0c56f`、`a87ff8e` | 修订锚点，让"这个数是在哪个修订上测的"可追 |
| **实测数值 / 公式推导 / 失效模式分析** | `6.146729e-08`、`½·a_max·Δt_sub² ≤ bound`、"若退回前向欧拉则误差 6.946e-4 m" | **注释里最值钱的部分**，一个字都不许删 |

### 1.3 改写原则：**把时间锚换成功能锚**

删掉标签后，注释不能变得空洞 —— 要把"什么时候写的"改写成"**指的是哪个东西 / 为什么**"。

| 前 | 后 |
| --- | --- |
| `Day 4 切片 C ② 的 R-C 修复后由 16 提升为 128` | `R-C 修复后迭代预算由 16 提升为 128`（**保留 `R-C`**）<br>⚠ 本行仅**示意改写风格**；`128` 是当时 `MaxToiIterations` 的取值，**若该常量变更，本示例不随之更新**（避免规范自身成为过期数字的又一副本） |
| `Day 4 切片 A：单球 + 球-库边 + 袋喉越界冻结` | `单球 + 球-库边 + 袋喉越界冻结` |
| `瞄准与力度属 Day 8–10` | `瞄准与力度属交互层` |
| `实测事实（Day 2 AxisProbe 48 候选穷举 + Day 3 场景实测）` | `实测事实（AxisProbe 48 候选穷举 + 场景实例化实测）` |

> **⚠ 第一版示例写错了（由实际执行者发现并纠正）**：我原先把
> `Day 4 切片 C ② 的 R-C 修复…` 整句改成 `迭代预算由…`，**连 `R-C` 一起去掉了** —— 那是错的。
> **`R-C` 不是批次号，是风险登记表（`R-A`…`R-H`）里的风险条目 ID**，spec、测试、
> `d4-rc-diagnosis.json` 都用它指代同一件事 ⇒ **属于 §1.2 必须保留的锚点**。
> **正确做法：只删 `Day 4 切片 C ②` 这类开发日/批次标签，保留风险条目 ID。**

| `Day2 与 Day3 各写了一份 ResolveReportPath` | `TableIntegrityValidator 与 MaterialVisualValidator 各写了一份 ResolveReportPath` |
| `本类同时补上 Day1 —— Day1 此前完全没有 -outputDir` | `本类同时补上工程配置入口 —— 它此前完全没有 -outputDir` |
| `Day1/2/3/4 四个验收器` | `四个验收器（工程配置 / 数据完整性 / 材质视觉 / 物理）` |

> **关键**：旧注释里的 `Day1/2/3/4` 往往**指代的是现在已改名的组件**。
> 映射见 `Docs/工程标准.md` §9「标识符更名对照表」：`Day1 入口 → ApplyProjectConfig*`、
> `Day2 验证器 → TableIntegrityValidator`、`Day3 验证器/视觉 → MaterialVisualValidator / MaterialVisualSetup`、
> `Day4 验证器/场景 → PhysicsValidator / GreyboxSceneSetup`。
> **这正是把"时间"换成"功能"最有力的方式。**

## 2. 雷区（改注释前必须先知道）

### 2.1 有检查在**扫描源码文本**

| 检查 | 扫什么 | 判据 | 后果 |
| --- | --- | --- | --- |
| `D4-PHY-01` | `Scripts/Runtime/Physics/*.cs` | 正则 `\b(Rigidbody|Collider)\b`，**只跳整行注释** | 这**两个词出现在行尾注释或字符串字面量里 ⇒ 假失败** |
| `D-3`（16 球确定性） | `PoolSimulator.cs` | 剥掉 `//` 后查禁用词；并断言升序遍历字面量存在 | 改注释安全；**但那行代码一个字都不能动** |

⇒ **规则：仅在 `Runtime/Physics/` 下，注释里不要出现 `Rigidbody` / `Collider` 这两个词。**
需要表达时改写为"物理引擎刚体/碰撞体类型"。

### 2.2 文档里有 `文件:行号` 式引用
增删注释行会让行号位移。⇒ **尽量保持行数不变**；若确实增删了行，**必须在提交信息里列出**，
以便同步文档里的行号引用。

### 2.3 不许当成注释处理的东西
- 代码本身（缩进、重排、表达式、`[Test]` 特性）
- **字符串字面量里作为数据的内容**：检查项 ID、路径、`schema` 名、断言消息里的技术数字
- `.meta` 文件
- `Docs/Reports/**` 与 `Docs/Reviews/**`（**历史实录，永不改写**）

## 3. 自检（不需要 Unity，必须做）

改完在提交前，**必须**证明"改的只有注释"：

```bash
git diff -U0 | grep -E "^[+-]" | grep -vE "^(\+\+\+|---)" | grep -vE "^[+-]\s*(//|///|/\*|\*|#)"
```
⇒ **输出必须为空**。任何命中都说明你改了**非注释行**，必须回退该处。

（`#` 用于 Python 工具；`*` 用于块注释续行。）

### 3.1 行尾注释是**例外**，但必须额外证明

上面那条命令会把「代码 + 行尾注释」的整行判为命中 —— 它**无法区分"改了代码"与"只改了行尾注释"**。
（这是本规范第一版的缺陷，由实际执行者发现。）

⇒ 若要改行尾注释（例：`importer.isReadable = true; // 供 …（Day 2 必需）`），
**必须额外证明「`//` 之前的代码部分逐字节未变」**，并在**提交信息里给出该证明**
（例如用 `git diff` 显示：替换前后该行 `//` 左侧完全相同）。仅当证明成立时，该行才可改。

### 3.2 字符串字面量**不在本规范的范围内**

`[MenuItem("…Day-1…")]`、`Debug.LogError("Day-4 …")`、`CheckResult.Ok("RUN-01","Day-1 …")`
这类**字符串是行为与证据文本**，不是注释。改它们会：**改变产品界面 / 日志 / 并被写进 `Docs/Reports/*.json`**。
⇒ **本规范只约束注释；字符串字面量的文案另议。** 遇到时**不要改**，在报告里列出来。

### 3.3 Python 区**必须改用 AST 等价性证明**（§3 的 grep 对 docstring 原理失效）

Python 的 docstring **不以 `#` 开头**，所以 §3 那条 `grep -vE '^[+-]\s*(#…)'` 判据
**在 Python 上原理上不可能为空**（docstring 正文永远不被豁免）。⇒ **Python 区改用下法**：

- **只改注释/docstring 时**：剥掉 `Module`/`ClassDef`/`FunctionDef` 的 docstring 后比对 `ast.dump` ⇒ **必须完全一致**。
- **允许改字符串字面量时**（如"输出文案"类任务）：把**所有** `Constant(str)` 的值归一化为 `<STR>`
  后比对 `ast.dump` ⇒ 一致即证明**差异只在字符串的值、无任何结构变化**；
  并附 `git diff --numstat` 证明**行数无增删**。

> 此法由 Python 区执行者提出并实证（`Docs/Tools/*.py` 输出文案去 Day 标签），**强于 §3 的 grep**。

> ⚠ **该判据的边界（同由执行者补充，很重要）**：它**只能**证明
> 「**差异只在字符串的*值*、无结构或非字符串常量的变化**」，
> **不能**证明「改的是**用户可见的输出文案** 还是 **内部字面量**」——
> 二者**同属 `Constant(str)`**（例：`tempfile.mkdtemp(prefix="d2t04_")` 也是 `Constant(str)`）。
> ⇒ 后者仍须**人工按"是否用户可见"逐条判定**，并把判定结果写进报告的
> **「未改项清单 + 理由」**（本工程已有此体例）。
> **不得**把 AST 等价性证明当作"改动范围正确"的充分证据。
