### 2.3 要**定义式改写**才能诚实实现的（用户原话 → 可判定形式）

### 2.5 开球线（kitchen）—— 已定值 + 契约 + 一条命名陷阱
**取值（由既有常量派生，不新增字面量 ⇒ 铁律 16）**
```csharp

public const float KitchenLineX = ClothHalfLength / 2f;   // = 1.27 / 2 = +0.635 m
// 合法放置区（kitchen）= x > KitchenLineX（严格不等式：球心恰在线上 ⇒ 不合法）
```
**推导链（可回读）**：标准 8 球头线 = **头库前 1/4 台长** ⇒ `ClothHalfLength − ClothInnerLength/4 = 1.27 − 0.635 = +0.635`。
⚠ **口径来源如实标注**：**权威数据里没有头线定义** —— `Docs/Reference/gameplay-markers-reference.json:4509` 只有 `foot_spot_physics2d`，且 `:4525` 逐字写明 *"tuning is not a final engine specification"*；`table-metadata-reference.json` 相关命中全是几何/球袋坐标。⇒ **本值是"按其标准值推导"，不是数据里有的。**
**排除镜像口径（口径 B，头线 = −0.51）的依据**：`PhysicsTestDrive.cs:552-556` 自陈「**白球在头区、球堆在脚点**…相距 ≈ 半个台长 1.27 m」⇒ 白球开球位 = `RackApexX + ClothHalfLength` = −0.30 + 1.27 = **+0.97**；**只有口径 A（头线 +0.635）才让开球位落在 kitchen 内**，口径 B 会与代码自陈冲突。

## 3. 规则层（**新文件**，纯函数优先）

### 3.1 分层原则
- **判定与施加分离**：规则判定 = **纯函数**（输入：规则状态 + 本杆事实；输出：裁定）；施加（切回合、发自由球、记分）= 薄宿主。
- **AI 与规则的唯一接口**（`engineering-lead` 提的形状，采纳）：
  `RuleVerdict Judge(in RuleState before, in RuleFacts shot)`，其中
  `RuleFacts` = **首碰球号 + 本杆每颗球是否碰库（去重）+ 入袋球号 + 非入袋离台球号 + 白球是否落袋/离台**。
  ⇒ 这个 `RuleFacts` **正好全部来自 §2.1/§2.2 的出口**，不需要 AI 或 UI 反向耦合。

### 3.2 状态机（新概念，**另起名字**）
- `RuleState`：`openTable | assigned(solid|stripe)`、`turnSide(player|ai)`、`remaining[2]`、`matchScore[2]`、`rackIndex`、`mustShootForward`（kitchen 自由球专用）。
- ⚠ **命名**：UI 里已有的 `PracticeHudState.IsPlayerTurn(phase)` 是**相位判断、不是真回合** ⇒ 新概念**不得复用 `IsPlayerTurn`/`turn` 同名**（本批刚立过"同名不同义"的规矩）。

### 3.3 规则要点（按用户原话，逐条落成判据）
1. **开放球局**：开球进球**不定组**；**开球后第一颗合法进球**才定组（solid/stripe）。
2. **有效开球**：`≥1 颗进袋` **或** `≥4 颗目标球碰库（按球号去重）`；否则判**重摆**（或按用户口径定为犯规 —— **待用户确认**，见 §7 开放项）。
3. **开球黑 8 进袋**：黑 8 **拿回放球点**（`footSpot`）、**继续打、不算赢**。
4. **开球犯规（白球落袋/离台）**：对手得**开球线后自由球**（kitchen），**只能往线前击球** ⇒ `mustShootForward`。
5. **常规击球**：① 首碰必须是**自己组**的球（开放球局除外）② **碰库原则**：母球碰球后**任意球碰库**或有球进袋 ③ 违者犯规 ⇒ 对手**全场自由球**。
6. **直接判负**：未清完本方组就打进黑 8 ／ 打进黑 8 同时犯规（白球落袋/离台）／ 黑 8 离台。
7. **胜负**：清完本方组 → **合法**打进黑 8 ⇒ 本局胜。

## 4. AI 层（**新文件**）

### 4.1 关键前提（实测/推得已标）
- ⛔ **现有 `ShotPredictor.Predict` 只推演到"首次球-球接触"为止**，**答不了"这杆进几颗"** ⇒ AI 必须走**整杆推演**（用同一内核 `Step()` 到全部球静止）。该路径已被 `break_probe` 实测跑通。
- ✅ **确定性有既有判据**：`T37` 判据 6 用 `AssertBitIdentical` 断言"同输入两次推演逐位相同" ⇒ **AI 可以真的预演**。
- ✅ **杆只有 2 个自由度**：方向 + 力度（`Launch()` 无参，读 `aimDegrees`/`power`；`BallState` 无旋转）⇒ 候选空间小。
- ✅ **不撞渲染闸门**（纯 CPU 探针仿真，不建渲染器/材质）。
- ✅ **AI 回合的视觉态已存在**：`HudVisualState.AiTurn`（枚举/色/图标/文案齐全），只是被登记为**不可达**。

### 4.2 代价与预算（必须摊帧）
- 单次整杆推演：**开球 ≈5–61 ms**、普通直杆 **≈1–5 ms**（实测）；`Predict` 平均 ≈29 ms（**推得**，本卡要求补实测）。
- **硬规矩**：**单帧 ≤1 次整杆推演**；用 `AiTurn` 显示"思考中"，把 N 次**摊到多个渲染帧**；**N ≤ 64** 上限，超时（>1.5 s）用当前最优收尾。
- **两段式**：粗筛 5° → 精 0.5°，把 ~720 次压到 **≈46 次**。
- **分配**：AI 必须复用 `workspace` 重载（`ShotPredictor.cs:59`）并**自持可复用探针**（`:84` 是否已缓存 **待确认**）。

### 4.3 参数面与难度表（§1-D2，**已按用户"不要太强"整体下调**）
> **设计原则（用户原话：「先由你定，但不要太强」）**：
> ① **三档共用同一套候选生成 / 整杆推演 / 评分代码**，**只换参数**（⇒ 差异可归因、可断言字面量）；
> ② **全档不做两杆前瞻** —— 前瞻是最容易把 AI 变成"神"的一项，**本卡一律不要**；
> ③ **Expert 也保留可见失误**：方向 σ **不得小于 0.5°**、力度误差 **不得小于 5%**（**这是"不要太强"的可判定上界**，写在判据里，防止后续被人"顺手调神"）；
> ④ 目标手感：**能打、会犯错、但不会自己送** —— 玩家赢一局要有"我赢了"的实感，而不是"AI 放水"。

| 参数 | **Casual** | **Club**（默认） | **Expert** |
|---|---|---|---|
| 方向采样步长（粗 / 精） | 6.0° / 2.0° | 4.0° / 1.0° | 2.0° / 0.5° |
| 力度档数 | 3 | 4 | 6 |
| 瞄准角误差 σ（每次出杆抽样） | **±4.0°** | **±2.2°** | **±0.8°** |
| 力度误差 | ±25% | ±14% | ±6% |
| 选杆策略 | top-5 内**随机** | top-3 内**随机** | 取最优 |
| 走位评分 | 不评 | 不评 | **弱评**（只惩罚"白球落袋 / 白球贴库"两项） |
| **前瞻** | **无** | **无** | **无** |
| 每回合推演预算上界 | ≤16 次 | ≤32 次 | ≤64 次 |
| 超时（>1.5 s）收尾 | 用当前最优 | 同 | 同 |
| **可观测差异**（同台面、固定种子） | 中近台也常丢；常把黑 8 打飞 | 中近台较稳、**远台常丢**、不做位 | 中近台几乎不漏、**远台仍会丢**、走位一般 |

**判据（P4）**：
1. **三档参数可断言字面量**（纯数据表，逐字段比对）；
2. **上界守**：`σ_Expert ≥ 0.5°` 且 `力度误差_Expert ≥ 5%`（"不被调神"的可判定反面）；
3. **可观测差异**：固定种子的 N 个抽样台面下，**合法进球杆成功率 `Casual < Club < Expert`**（**严格不等**，避免三档等价）；
4. **预算守**：单帧 ≤1 次整杆推演、每回合 ≤ 对应上界、超时用当前最优收尾；
5. **负路径**：去掉合法性过滤 ⇒ AI 会打出犯规杆 ⇒ 必红。

## 附：P5-A 落下的两条工程纪律（**写进规格，不只写在脚本里**）

### 附-1　注入的备份必须与「当前字节」对齐（`backup` 之后**不得**再改产品文件）
**事故（实测）**：在 `backup` **之后**又改了产品文件（加 `PrepareProbe` 重构），随后 `restore` 用**改动前**的备份覆盖 ⇒ **静默回滚**了产品改动（编译立刻报 `AiCandidatePots` 不存在）。
**机制（强制）**：注入脚本必须
1. `backup <dir>` 时把当前 sha1 写成 `<dir>/baseline.sha1`；
2. `apply-* <dir>` 前**断言 `当前 == baseline`**（不等即拒绝注入）；
3. `restore <dir>` 后**回读并断言 `== baseline`**，不一致即报错（不许静默）。
⇒ 一句话：**「备份」与「注入」之间的产品文件必须冻结**；否则还原的是别人的中间态。

### 附-2　跑批互斥（工具：`Docs/Tools/batch_lock.sh`）
**为什么必须机械化**：`unity_batch.sh tests` **起跑前会删旧结果 XML** ⇒ 两人同时跑的真实危险不是"跑不成"，而是**互相把对方的结果读成自己的**（**假证据**）。
**规则**：① 锁在**仓外** `%TEMP%\billiards_batch\BATCH_LOCK`（内容 = 持有者 + PID + 起始时刻）；② 起跑前若锁存在且 **PID 存活 + 新鲜** ⇒ **让路**；**PID 已死** ⇒ 判为残留、**可接管并留痕**；③ 跑完删锁；④ **绝不删 `Temp/UnityLockfile`**（那是 Unity 自己的）；⑤ 结果只认「**自己那次**跑批的 mtime + 自己的锁持有窗口」（锁窗口之外的 XML 一律不得引用）。
