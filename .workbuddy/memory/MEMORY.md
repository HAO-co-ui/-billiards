## 卡 35-A 的验收标准（照抄策划，不可放宽）
- 唯一验证假设：击球瞄准的物理手感 + 进球瞬间的爽感，能不能让人"再来一杆"。
- 必须保质保量到 80 分：**瞄准线清晰、力度控制跟手、物理弹库真实、进球有"清脆"反馈**。
- 可以糙：美术 3D 低模球桌即可；先 1 张球桌。
- 成功看的数据：单局时长、进球率、再来一局率、次日留存。
- 备注（决定了排期重心）：**"物理不真就'台球乱弹'"** —— 这是最核心的一张卡。

## 硬性架构约定（不要推翻）
1. **台球物理自研 2D 定长步进，禁用 Unity PhysX。** 原因：球半径 0.028575 m + 初速 2–8 m/s，
   PhysX 离散检测在球堆开球时穿透；且无确定性 → 瞄准预测 / AI 推演 / 回放全废。
2. 物理在**规范米制二维平面**（长轴 × 短轴）运算，渲染层映射 `(x, 0, y)` 到三维。
3. **单位 = 米**。硬指标：内库 2.54 × 1.270108866 m、球半径 0.028575 m、台呢 y = 0、
   杆长 1.4 m（杆尖为局部原点、杆身 +Z）。
4. **"桌面扩大 20%" 只做视觉**：`PlayfieldRoot` 缩放 1.2，物理保持规范米制，指针拾取反向映射。
5. 所有手感参数外置为 ScriptableObject（库边弹性/台呢滚阻/球-球恢复/袋口半径/力度曲线），
   目标是 5 分钟内改一个值重测。

## 坐标系与手性约定（Day 2 实测确立，不可推翻）
- **唯一转换点**：`Assets/_Project/Scripts/Runtime/Core/PoolGeometry.cs`。
  禁止在其他任何位置再做轴/手性/缩放变换。ADR 见 `Docs/adr/ADR-0001-坐标系与手性约定.md`。
- 模型轴修正：`(m.x, m.y, m.z) → (−m.x, m.z, m.y)`（纯旋转，det = +1）。
- 物理 → Unity：`PhysicsToUnity = (px, h, py)`，与规范约定 `(x, 0, y)` 一致，X/Y 均无符号翻转。
- **反直觉事实（穷举 48 候选实测得出）**：球桌 FBX 的 metadata 声明 `UpAxis=Y`，
  但**顶点实际是 Z-up**，且 Unity 导入时把 X 取反。按声明处理会错。
  正确修正的端点对齐误差 **0.261 mm**，次优候选 **640 mm**（差 2400 倍，判据极强）。
- `py` 符号是**规范自由度**：本桌短轴中线近乎镜像对称（~1e-6 m），两符号候选差 1.25e-4 mm
  （float 噪声级），数据上不可判别。已按规范约定选定，可观测影响 < 0.3 mm。
- 手性自检判据（不依赖基线，故能抓镜像）：袋口符号模式 `[+,−,−,−,+,+]`；
  82 段拼接绕向 shoelace = **+3.144285（CCW）**。
- **容差陷阱（实测）**：镜像/180° 旋转在"顺序无关 + 1 mm 容差"下差异仅
  4.74e-4 / 1.04e-4 / 4.73e-4 m，会被漏检。逐点比对必须**索引对齐 + 容差 1e-5 m**；
  顺序无关比对容差须 < 1e-4 m。**180° 旋转时所有自包含判据都失效**，只有索引对齐逐点比对
  能靠 0.277 mm 的不对称区分。

## 验收与证据的铁律（Day 2 建立）
1. **永远不要在替换证据产出之前删除最后的已知良好证据。** 证据文件的价值在于
   "它记录了一个真实发生过的通过状态"。正确顺序：先跑出新的并确认成功，**然后**才清理旧的；
   或把旧的改名保留（如 `day2-verification.20261013T1207.json`）**删除也是写操作**，同样适用
   "先落盘再退出"原则。Day 2 实际后果：`day2-verification.json` 一度完全缺失，
   没人能回答"上次校验通过是什么时候、多少项通过"。
2. **"写了 N 项检查"不等于"运行并观察到 N 项通过"** —— 报告只允许写后者。
   Day 2 实例：复核方的 6 项审计测试因其文件编译不过（CS0136），在修复前**从未真正跑起来过**。
3. **任何否定性结论（"字段缺失"、"0 处命中"、"查不到"、"未发现"）必须用第二种独立方法
   复核后才能写进报告。** 否定性结论是静默工具失效最容易藏身的地方：正向结论错了通常会被
   后续检查撞出，而"什么也没找到"本身就是否定性结论预期输出的样子。
   Day 2 实例：主理人用 `python -c` 内嵌正则 grep `rail:` 得 0 处，误报为"字段被静默丢弃"，
   实际有 82 处（真因是 shell 破坏了 `\s`/`\S`，findall 静默返回空）。
   ⇒ 含正则的 python **一律写成文件再执行**。
4. **不得以删除检查作为让套件变绿的手段。** 容差被误用时，纠正**推导依据**而保留检查。
   更有效的机制是：**把实测值本身写进检查输出**，而非只输出 PASS/FAIL —— 阈值只能拦大错，
   记录实测值才能看见渐变漂移。
5. **派发复核之前必须先冻结被复核物。** Day 2 教训：先派复核、后下修正指令，
   导致复核对象在复核中被移动（校验项 29→31、测试 35→37）。
   补救手段是**修订指纹（SHA256）锚点** + 要求报告记录"结论对应哪个版本"。
6. **锚点指纹必须在"冻结已确认"之后取。** 在冻结之前取，锚点会在下发前就过期
   （Day 2 实例：主理人在 12:08 取指纹，工程侧随后又改了 2 个文件，锚点表有 2 项已过期）。
7. **关于状态的断言必须带时刻，或在使用前重新验证。** "工作区是干净的"这类说法在并发协作下
   说完即可能过期。并发编辑期间的"已验证"要附具体修订/时刻，或改述为"我在 T 时刻观察到 X"。
8. **不要用 `git add -A` 提交，尤其在队友并发编辑时** —— 它会把别人进行中的改动扫进自己的提交，
   套上一个不描述它们的提交信息，稀释可追溯性（Day 2 实例：名为"追加 §十三"的提交实际含 41 个文件）。
   用**显式路径**提交。
9. **一个检查的容差若来自"对误差成因的解释"，该解释本身必须先被证伪检验过。**
   否则容差不只可能过松，还会把错误的成因写进文档，误导后来者。
   （Day 2 实例："轮廓近似残差"解释被 FBX 直解证伪 —— 端点其实精确贴合网格面，
   0.2613 mm 只是"最近顶点"度量的采样下限。）

## 手性与网格对应的容差（两类不可混用）
- **数据集 ↔ 数据集**（同一批点的两种表示）：索引对齐，容差 **1e-5 m**。
- **物理数据 ↔ 渲染网格**：
  - ✅ **已证**（Day 2 追加复核，经自写 FBX 二进制解析器独立确认）：
    188 个库边/袋口端点**全部精确落在网格面上（最坏 0.000000 m）**。82 段线段**精确贴合**网格。
  - ⚠️ **"轮廓近似残差 0.2613 mm"的解释已被证伪**（它曾被我采纳并据此定了 0.5 mm 容差）。
    那 0.2613 mm **完全来自 `AXL-04/05` 用"最近离散顶点"度量** —— 是**采样下限**而非几何残差
    （最坏端点落在边长 2.5~3.6 mm 的三角形内，离最近顶点自然 ~0.26 mm）。
  - ⇒ **正确做法**：度量改为"最近网格**面点**"（当前精确为 0），阈值收紧至 **1e-4 m**。
    若坚持"最近顶点"，阈值**必须由局部顶点间距导出**，不可拍板 ——
    否则阈值随网格细分密度漂移，网格变粗会误报。
  - **衍生教训**：一个检查的容差若来自"对误差成因的解释"，那么**这个解释本身必须被证伪检验过**。
    否则容差不只可能过松，还会把错误的成因写进文档，误导后来者。
- **任何镜像/旋转判定禁止依赖顺序无关比对。**

## 工程配置的铁律（Day 1 建立，务必遵守）
1. **绝不用手改 `ProjectSettings/*.asset`。** Unity 把工程设置常驻内存，编辑器运行期间手改磁盘
   YAML 会在它下次写回时被静默覆盖（实测：`ProjectSettings.asset` 在编辑器启动时被自动重写）。
   一切配置改动写进 `Assets/_Project/Scripts/Editor/ProjectSetup/BilliardsProjectSetup.cs`，
   通过官方 API 应用。该脚本幂等、可复现，并且是这套配置的唯一文档。
2. **验收与配置同源**：`BilliardsProjectVerifier.cs` 提供 26 项检查，配置器执行后自动调用。
   命令见 `BilliardsProjectSetup.ApplyDay1FromCommandLine`（也可用菜单 `Billiards → Setup → ...`）。
3. **判断资产是否存在必须查文件系统**（`ProjectPaths.Exists`），不要用
   `AssetDatabase.LoadAssetAtPath<Object>() != null`。后者在资产因依赖脚本被删而变为
   "不可反序列化"时返回 null，会造成**清理与验收同时静默失效**的假通过。
4. **`Temp/UnityLockfile` 陈旧残留**会让批处理在"加载程序集"后静默退出（退出码 1、日志无错）。
   无 Unity 进程运行时可直接删除该文件后重试。
5. 批处理下 `EditorSceneManager.NewScene` 必须用 `NewSceneMode.Single`（起始场景未命名未保存，
   Additive 会被拒）。
